# Interactive-App Items — Design (Phase 8)

**Status:** approved 2026-06-28 (brainstorming); revised 2026-06-28 after a 5-reviewer panel + two codex passes.

**Goal:** Let course admins author `interactive_app` items (an external app embedded by URL) and let students view them, completing the last unimplemented content type. The backend already models this; this slice is **frontend-only**.

## Context

`interactive_app` is one of the five student-side `Item` types (`static_page`, `video`, `quiz`, `mini_project`, `interactive_app`) and one of the **four authorable** `AdminTreeItem` types (`static_page`, `video`, `quiz`, `interactive_app` — `types.ts:230`). The backend is already complete:

- `Item.script_url` (`String(500)`, nullable) — the app URL (`backend/mathion/models.py:114`).
- `ItemCreate`/`ItemUpdate`/`ItemResponse` carry `script_url`; create **requires** it for interactive_app (`schemas.py:113–119`) and both create and update validate the scheme with a case-sensitive `startswith(("http://","https://"))` (`schemas.py:104–109, 140–145`). `_ITEM_EDITABLE_PUBLISHED` includes `script_url`, so it is editable on **published** versions too (`backend/mathion/api/items.py:16`), exactly like `video_url`. `update_item` also rejects nulling `script_url` for an interactive_app (`items.py:205–207`).
- The student content endpoint serves `script_url` in both the version-content block serialization and the per-item shape (`backend/mathion/api/content.py:174, 205–206`).
- `frontend/src/lib/types.ts` already declares `InteractiveAppItem = ItemBase & { type: 'interactive_app'; script_url: string }` (lines 93–96), includes it in the `Item` union (58–63), and `AdminTreeItem.script_url` exists (line 234) — **no types change needed**.

The frontend is the gap:
- **Student render:** `ItemRouter.svelte:21–22` maps `interactive_app` → `<UnsupportedItem>` (a placeholder).
- **Authoring create:** `ItemTypePicker`'s union is `'static_page' | 'video' | 'quiz'` (`ItemTypePicker.svelte:6`) — interactive_app is not offerable.
- **Authoring edit:** `ItemEditPage` excludes interactive_app from `editable` (`ItemEditPage.svelte:45`) and shows a read-only *"Interactive-app editing lands in slice 2"* note in the final `{:else}` branch (`ItemEditPage.svelte:341–347`).

The closest existing analog is the **`video`** item type: a URL → iframe on the student side, a required-URL create field, and a URL edit form with live preview. This slice mirrors `video` throughout, **except** for the deliberate differences listed below.

### Deliberate differences from `video`

1. **Sandbox** — the interactive iframe is sandboxed (`sandbox="allow-scripts"`, no `allow-same-origin`) and adds `referrerpolicy="no-referrer"`; `VideoFrame` has neither (it sets `allowfullscreen`, which the interactive frame omits).
2. **No URL normalization** — `video` runs `normalizeVideoUrl` (YouTube/Vimeo watch→embed rewrite) before `safeIframeUrl`; interactive_app runs the `safeAppUrl` wrapper (Decision 6) only, on both the player and editor sides, and PATCHes the URL verbatim.
3. **Auto-coverage** — no "mark as done" button; opening the item auto-covers it (see Decision 2).
4. **Fixed sizing** — fixed height × full width, not `VideoFrame`'s 16:9 aspect ratio.
5. **Player-side sanitization + mixed-content guard** — `VideoItem` iframes `item.video_url` **raw** (`VideoItem.svelte:33`); `InteractiveAppItem` sanitizes with `safeAppUrl` (which also rejects an `http://` app on an `https://` page — Decision 6) and shows a notice on `null`. This is a strict improvement, not literal parity. The guard matters here precisely because coverage is automatic (see Decision 6).

## Decisions (from brainstorming + review)

1. **App source:** external URL only. Admin hosts the app elsewhere and pastes a URL. Asset-hosted bundles are out of scope.
2. **Coverage + time-on-task:** auto-covered on view, and time-on-task is tracked like every other timed type. On entering the item the player runs an `$effect` keyed on `item.id` that `start()`s a `createCoverageTracker(item.id)` (so active time accrues for the teacher dashboards, which read `time_spent`) and, when not already covered, fires `markCovered()` + `markItemCovered(item.id)` **once**; cleanup `stop()`s the tracker (flushing accrued time). This is intentionally the laxest coverage of any type (`static_page` covers after 30s, `video` on a button, `quiz` on submit, interactive_app at 0s on view) — the user chose "opening it counts." Without `start()`/`stop()` the item would report `time_spent = 0` forever; we add them so the design genuinely mirrors video's time tracking.
3. **Sizing:** full width × a fixed height (`600px` as a sensible default; exact value is a later styling pass); content scrolls within the frame. No per-item height field (no backend change).
4. **Sandbox:** `sandbox="allow-scripts"` **without** `allow-same-origin`, per the platform spec's trust model (`docs/superpowers/specs/2026-04-19-mathion-platform-design.md` line 105). Excluding `allow-same-origin` keeps the app in an opaque origin (no parent DOM/cookie/storage access, no access to the Mathion session). The "`allow-scripts` + `allow-same-origin` voids the sandbox" rule fully applies only when the framed content is *same-origin to the embedder* (it could then script away the `sandbox` attribute); the apps here are external-origin, but `allow-same-origin` is still excluded because it would restore the app's own-origin storage/cookies and weaken isolation. Also add `referrerpolicy="no-referrer"` so the third-party app host never receives the Mathion page URL (which encodes course/run/sequence ids). **Never add** (each re-opens a concrete vector): `allow-same-origin` (de-isolation), `allow-top-navigation`/`allow-top-navigation-by-user-activation`/`allow-top-navigation-to-custom-protocols` (tab-hijack / custom-protocol phishing), `allow-popups-to-escape-sandbox` (un-sandboxed attacker windows), `allow-downloads` (drive-by downloads), `allow-modals` (dialog spoofing), `allow-storage-access-by-user-activation` (Storage Access API → first-party storage). **Discouraged, not forbidden** (do not breach parent isolation; add only if a real app needs it): `allow-forms` and `allow-popups` — but `allow-popups` still carries new-tab phishing risk and must never be combined with `allow-popups-to-escape-sandbox`. Apps are admin-trusted ("comparable to installing a plugin," per the platform spec); the sandbox blocks parent-DOM/cookie/storage access but not the app's own network requests.
5. **Approach:** dedicated components that mirror `video`; **do not** refactor `video`/`VideoFrame` into a shared abstraction (the differences above would make it leaky and would risk the working video path).
6. **Mixed content (client-side guard, not a backend change):** an `http://` app embedded on an `https://`-served Mathion is blocked by the browser as mixed content and cannot render — and because cross-origin iframe load failure is **not** detectable from JS (the `error` event doesn't fire, and `load` fires even when content fails), the auto-cover-on-view design would otherwise credit coverage for an app the student never saw (phantom coverage). Mitigated **frontend-only** with a `safeAppUrl` wrapper that rejects `http:` when the page protocol is `https:` (still allowed on `http` dev deployments — the check keys on the page protocol, not a hardcoded scheme). This is a real difference from `video`, which auto-covers via a human button (a blank frame won't be falsely covered) and needs no such guard. The backend still stores `http://` (no backend change here); server-side https enforcement stays out of scope.

## Architecture & components

### Shared helper
- **`lib/safeAppUrl.ts`** (new, thin wrapper over `safeIframeUrl`): `safeAppUrl(value, pageProtocol = window.location.protocol)` returns `safeIframeUrl(value)`, but additionally returns `null` when the accepted URL's protocol is `http:` and `pageProtocol === 'https:'` (the mixed-content guard, Decision 6). The `pageProtocol` parameter is a test seam (mirrors `createCoverageTracker`'s `now` seam). Used by `InteractiveAppItem` (render) and `ItemEditPage`'s live preview, read-only preview, and Save gate. Also update the stale `safeIframeUrl.ts:4` doc comment ("Used by the video-item editor preview…") to mention the interactive-app surfaces. `video` is untouched (it keeps using `safeIframeUrl` directly).

### Student player
- **`components/items/InteractiveFrame.svelte`** (new, parallels `VideoFrame`): a fixed-height (`600px` default), full-width iframe wrapper. Renders `<iframe {src} {title} sandbox="allow-scripts" referrerpolicy="no-referrer">` (no `allowfullscreen`). Shared by the student player and the editor's live preview and read-only preview (as `VideoFrame` is). Caller passes an already-sanitized `src`.
- **`components/items/InteractiveAppItem.svelte`** (new, parallels `VideoItem`): receives `{ item: InteractiveAppItem; isCovered: boolean }`. Computes `safe = safeAppUrl(item.script_url)`. Renders the title + `<InteractiveFrame src={safe} title={item.title || 'Interactive app'} />`. Coverage/time tracking lives in an `$effect` keyed on `item.id` (NOT `onMount` — `ItemRouter` is not keyed by `item.id`, so navigating between two interactive_app items reuses one component instance and only the effect re-runs; `VideoItem.svelte:13–17` is the pattern):
  - capture `const id = item.id` and reuse it for both `createCoverageTracker(id)` and `markItemCovered(id)` (reading `item.id` again *after* the `markCovered` await could mark the wrong item after a fast navigation);
  - if `safe` is `null`, return early — no tracker, no coverage (don't credit an app the student can't see), render a "This interactive app can't be displayed" notice instead of the iframe;
  - otherwise create the tracker, `start()` it, and fire coverage once when not already covered: `if (!untrack(() => isCovered)) void tracker.markCovered().then(() => markItemCovered(id))`. Reading `isCovered` via `untrack` is what makes the once-only guarantee hold — it stops the `markItemCovered` store write from re-invalidating this effect, so the only re-runs are genuine `item.id`/URL changes (a new item that *should* re-cover). **No separate latch is needed**: there is no self-triggered re-run left to guard, and a latch that persisted across re-runs would wrongly suppress covering the next item. (`VideoItem` reads `isCovered` only in its template, never in its effect — we must read it in the effect to decide auto-cover, hence `untrack`.)
  - cleanup `stop()`s the tracker (flushing accrued time).
- **`components/items/ItemRouter.svelte`**: replace `<UnsupportedItem type="interactive_app"/>` (lines 21–22) with `<InteractiveAppItem {item} {isCovered} />`. `isCovered` is already derived and in scope (`ItemRouter.svelte:10`).

## Data flow

Create (`POST /sequences/{sid}/items`, `type=interactive_app` + `script_url`) → edit (`PATCH /items/{id}` `script_url`; allowed on created **and** published) → student `GET` version content serves `script_url` → `InteractiveAppItem` sanitizes via `safeAppUrl` and embeds in the sandboxed `InteractiveFrame` → an `$effect` keyed on `item.id` starts time tracking and auto-marks coverage once.

## Error handling & edge cases

- **Unsafe/blank `script_url` at render:** `safeAppUrl` returns `null` → show a "can't be displayed" notice, skip the iframe, and skip tracking + coverage (don't credit coverage for an app the student can't see). Consequence acknowledged: a *required* interactive_app item with an un-renderable URL can never be covered, so the student is blocked from completing the block; the `scriptUrlInvalid` Save gate above is what keeps such a URL from being published in the first place.
- **Mixed content (mitigated client-side):** the backend accepts `http://` and `safeIframeUrl` returns non-null for it, but on an HTTPS-served Mathion an `http://` app iframe is **blocked by the browser as mixed content** and cannot render; since cross-origin iframe load failure is not detectable (the `error` event doesn't fire, `load` fires even on failure), auto-coverage would otherwise credit it (phantom coverage). `safeAppUrl` rejects `http:` under an `https:` page (Decision 6), so the player shows the notice and skips tracking/coverage, the editor preview blanks, and Save is blocked. `http` dev deployments still work (the guard keys on the page protocol). The backend still stores `http://`; server-side https enforcement stays out of scope.
- **Create/edit validation:** the create form requires a non-empty URL via the native `required` attribute; the edit form additionally blocks Save unless `safeAppUrl` accepts the URL. Backend is the source of truth for the scheme: its case-sensitive `startswith` rejects e.g. `HTTP://…` that `safeAppUrl` lowercase-accepts (a residual minor mismatch — harmless, since such a save just 422s). Where 422s surface differs by path: on **create**, a mapped 422 renders inline as `createErrors.script_url` (via `mapCreateError`); on **edit**, `save()`'s catch **toasts** the 422 (`ItemEditPage.svelte:203`) — edit-side field errors are not rendered inline (same as the video edit branch).
- **Auto-coverage idempotency:** the only auto-cover trigger is the `$effect`; reading `isCovered` via `untrack` means the `markItemCovered` write doesn't re-invalidate the effect, so it fires at most once per item view (and re-fires only on a genuine `item.id` change — a new item that should cover). The server `track` endpoint is itself idempotent for `is_covered` and additive for `time_spent`, so even a residual double-post is harmless.
- **Unmount-before-resolve:** if the student navigates away before `markCovered` resolves, the POST has no abort signal and completes in the background (best-effort); the post-await `markItemCovered(id)` is safe because it no-ops when the course/entry is gone, and `id` was captured at effect start.
- **Disabled version:** the edit form is already gated off on disabled/archived versions; interactive_app now renders the read-only preview branch (above) instead of a blank box.

## Testing

Frontend component tests in the established `mount`/`unmount`/`flushSync`/`tick` style (no `@testing-library`). **No existing standalone player test** (`VideoItem`/`PageItem`/`ItemRouter`) exists to copy — these are written from scratch; `ItemTypePicker.svelte.test.ts` and the harness-driven `ItemEditPage.refreshKey` test are the closest existing patterns. The coverage POST has no injectable seam from inside `InteractiveAppItem` (it creates the tracker with `item.id` only → `defaultPostTrack` → dynamic `import('./api')` → `api.post` → global `fetch`), so coverage assertions **stub `globalThis.fetch`** and **settle microtasks** (await several `Promise.resolve()`/`flushSync` cycles) before asserting — otherwise the async + dynamic-import path makes negative assertions pass vacuously. No backend changes → no new pytest.

- **`safeAppUrl`** (pure unit test, pass `pageProtocol` explicitly): returns the URL for `https://` on any page and for `http://` on an `http:` page; returns `null` for `http://` on an `https:` page; returns `null` for everything `safeIframeUrl` already rejects (empty, no-host `https://`, `javascript:`, etc.).
- **`InteractiveFrame`**: renders an `<iframe>` whose `sandbox` is exactly `"allow-scripts"` (regression guard against anyone adding `allow-same-origin`), `referrerpolicy` is `"no-referrer"`, `allowfullscreen` is absent, `src` is the passed value, and `title` is non-empty.
- **`InteractiveAppItem`** (stub `globalThis.fetch`): with a `safeAppUrl`-accepted URL + `isCovered:false`, after settling, exactly one POST to `/api/items/:id/track` with `is_covered:true` fired; with `isCovered:true`, after settling, **no** such POST; with a URL `safeAppUrl` rejects (`javascript:…` or `https://` no-host), the notice renders, no iframe, and after settling **no** POST; iframe `title` falls back to `'Interactive app'` when `item.title` is empty. (The `http`-on-`https` rejection itself is covered by the `safeAppUrl` unit test, avoiding a `window.location` stub here.)
- **`ItemRouter`** (stub `globalThis.fetch`, since mounting fires the coverage POST): an interactive_app item renders `InteractiveAppItem` (iframe present), not `UnsupportedItem` (its "isn't available" text absent).
- **`ItemTypePicker`**: widen the existing test's hard-coded `value` type; assert the interactive_app radio renders and `bind:group` updates `value`.
- **`SequenceAccordion`**: selecting interactive_app shows the required App URL field; submitting a title + URL includes `script_url` in the POST body (assert via the api/fetch stub). Do **not** test "empty required field click → POST → inline 422" — native constraint validation blocks the `submit` event before `submitCreate` runs (and jsdom's enforcement is unreliable). Instead test the error path directly: drive a submit with a stubbed 422 carrying a `script_url` loc and assert it maps to `createErrors.script_url` inline (this exercises the new `known`-array arm via `mapCreateError`).
- **`ItemEditPage`** (harness approach like the existing test: seed `currentEditorVersion.value`, stub `globalThis.fetch`, mock `listAssets`, pass route props): interactive_app is editable (edit form renders); Save is disabled when `safeAppUrl(script_url) === null` (the `scriptUrlInvalid` gate — the cheapest discriminating check); Save sends `script_url`; the live preview reflects a typed valid URL; a published version still allows the edit; a disabled/archived version renders the read-only preview, not a blank box.

## Accessibility

- The iframe carries a non-empty `title` (`item.title`, falling back to `'Interactive app'`).
- The new `ItemTypePicker` radio mirrors the existing radio-group a11y: decorative glyph `aria-hidden`, label-wrapped radio, `:focus-within` ring.
- The **edit** page App URL field uses a wrapping `<label>` (accessible). The **create** form's App URL field is placeholder-only (no `<label>`), inherited verbatim from the video create field — a known, **deferred** a11y gap; a fuller create-form label pass (covering title/content/video/app fields together) is out of scope for this slice.

## Out of scope (future slices)

- Asset-hosted app bundles (upload HTML/JS to course assets) — external URL only here.
- A `postMessage` completion/scoring protocol — apps are exploratory, not graded.
- Per-item configurable height (would require a new backend column).
- **Server-side** https enforcement for app URLs — the client-side `safeAppUrl` guard (Decision 6) already prevents phantom coverage and un-renderable embeds on HTTPS deployments; persisting only https in the backend (rejecting `http://` at the API, and/or aligning its case-sensitive scheme check with the client) is deferred hardening and would diverge from `video`'s `http(s)` acceptance.
- A CSP `frame-src` allowlist — the app has no CSP today and the URL is arbitrary-by-design, so the iframe `sandbox` is the primary control, not CSP; an admin-managed origin allowlist is a separate, larger feature.
- Relaxing the sandbox (adding any never-add token from Decision 4) — revisit only if a real, trusted app needs it.
- Fullscreen control for the embed.
