## 1. Scope

Close the high-impact **check-then-act** races A1 made fixable and testable. **Four lock-enforced invariants** across four advisory-lock domains; multi-user enrollment batches stay deadlock-free by processing their `users`-table writes in a normalized-email order rather than under a global lock (§3.2). (Invariant **#4**, `submission_number` collision, is already `UNIQUE`-enforced and folds into #3 — hence the table skips from #3 to #5, which keeps its original backlog number.)

| # | Invariant at risk | Trigger | Lock domain |
|---|-------------------|---------|-------------|
| 1 | a group must not exceed `MAX_GROUP_SIZE` (10) | admin roster writes (esp. bulk) | `CAPACITY(run_id)` |
| 2 | ≤ 1 active enrollment per (student, course) — **both** the `RunStudent` (run) and `StudentEnrollment` (version) tables | admin add / enroll / batch / publish | `ENROLLMENT(course_id)` |
| 3 | ≤ 1 *pending* submission per revision cycle per (mini-project, group); `submission_number` gap-free (folds in #4) | student (group members) | `SUBMISSION(mp_id, group_id)` |
| 5 | a mini-project locked by its first submission stays immutable except by course-admin `force` | student first-submit vs admin patch / delete-mini-project / delete-run cascade | `MINIPROJECT(mp_id)` |

**Concurrency profile (honest):** #3 is student-triggered (deadline rush); #5 crosses a student submit and an admin edit; #1/#2 race during **bulk** admin ops. This is a **correctness** slice — contention at a class's scale (≤200 students) is negligible once the `MINIPROJECT` hold is kept short (§3.3), so coarse locks are the right trade.

**Already race-safe — explicitly NOT in scope:**
- **quiz max-attempts** — `quiz.py:123-142` already does an atomic `UPDATE UserItemState SET attempt_count=attempt_count+1 … WHERE id=:id AND attempt_count < :max` + `rowcount==0 → rollback → 409`. Under READ COMMITTED the blocked writer re-evaluates the `WHERE` against the committed row (EvalPlanQual). No lock needed.
- **insert races caught by UNIQUE + retry:** `submission_number` collision (`UNIQUE(mp,group,number)`, `models.py:296`); get-or-create `UserItemState` (unique `user_id,item_id`). **`get_or_create_user` is NOW in scope** — see §3.1 (its recovery path must become SAVEPOINT-based before any lock is held across it).

## 2. Background — why these race, and why now

Each site does **read (check) → decide → write (act)** across multiple statements with no lock across the gap. Under READ COMMITTED (Postgres default, now pinned explicitly on the engine — §3.3), two transactions each read the pre-write state, both pass the guard, both write → invariant violated. SQLite's single-writer lock masked this; Postgres does not. A1 shipped the engine + harness that make advisory locks available and concurrent connections testable.

## 3. Mechanism — pessimistic advisory locking (no `FOR UPDATE` at any locked site)

### 3.1 The primitive + the `get_or_create_user` prerequisite (Task 1)

```python
LOCK_NS_ENROLLMENT  = 0   # key: (course_id)
LOCK_NS_CAPACITY    = 1   # key: (run_id)
LOCK_NS_MINIPROJECT = 2   # key: (mp_id)
LOCK_NS_SUBMISSION  = 3   # key: (mp_id, group_id)

def advisory_xact_lock(db: Session, namespace: int, *ids: int) -> None:
    """Transaction-scoped PostgreSQL advisory lock.

    Folds (namespace, *ids) into a deterministic signed 64-bit key via BLAKE2b
    (stable across processes — NOT Python's salted hash()), then calls
    pg_advisory_xact_lock(bigint). Released automatically on COMMIT/ROLLBACK.
    Distinct namespaces cannot collide (namespace is folded into the payload);
    a ~2⁻⁶⁴ BLAKE2b collision would only cause harmless spurious serialization.
    """
    payload = ":".join(str(x) for x in (namespace, *ids)).encode()
    key = int.from_bytes(hashlib.blake2b(payload, digest_size=8).digest(), "big", signed=True)
    db.execute(text("SELECT pg_advisory_xact_lock(:k)"), {"k": key})
```
`digest_size=8` → exactly the `bigint` range `[-2⁶³, 2⁶³-1]`; psycopg3 adapts it straight to `int8`. Empirically verified against SQLAlchemy 2.0.49 / psycopg 3.3.4 / PG17 (overload resolution, driver adaptation, xact-scope release, 4-key hold).

**`MAX_GROUP_SIZE = 10`** — unify **four** literals: `helpers.py:197`, `run_roster.py:149`, `run_roster.py:358`, and the publish readiness gate `runs.py:209` (`having(count > 10)`) + its `:212` message.

**Prerequisite — `get_or_create_user` must not do a top-level rollback (C1).** Its concurrent-insert recovery (`helpers.py:71-77`) currently calls **`db.rollback()`** (ends the transaction → releases every advisory lock) and then *continues*. Every enrollment path calls it while a lock is (or will be) held, so it must recover via a SAVEPOINT that unwinds only the failed insert:
```python
user = db.execute(select(User).where(User.email == email)).scalar_one_or_none()
if user is None:
    try:
        with db.begin_nested():           # SAVEPOINT — NOT a top-level rollback
            user = User(email=email, full_name=None)
            db.add(user)
            db.flush()
    except IntegrityError:
        user = db.execute(select(User).where(User.email == email)).scalar_one()
return user
```
Empirically confirmed on PG17: after the flush's `IntegrityError` the context manager issues `ROLLBACK TO SAVEPOINT`, the connection stays usable, `session.new` is empty (the failed `User` is expunged), the re-query returns the winner, and an advisory lock acquired *before* the savepoint is still held. This is Task 1 and gates every enrollment task.

### 3.2 Global lock-acquisition order (deadlock-freedom by construction)

> **Acquire locks in ascending namespace order: `ENROLLMENT(0)` → `CAPACITY(1)` → `MINIPROJECT(2)` → `SUBMISSION(3)`.**

Each domain's key is a single well-defined value per request. The multi-lock paths all ascend:
- `add_student`: `ENROLLMENT(course_id)` then `CAPACITY(run_id)`.
- `add_students_batch`: `ENROLLMENT(course_id)` then `CAPACITY(run_id)` — its per-row `users`-table writes are email-ordered, not lock-protected (§5.3).
- `enroll_batch`: `ENROLLMENT(course_id)` — its per-email `users`-table writes are email-ordered (§5.3).
- `create_submission`: `MINIPROJECT(mp_id)` then `SUBMISSION(mp_id, group_id)`.

Single-lock paths trivially comply: `patch_student`/`bulk_move` → CAPACITY only; `publish_run`/`enroll_student` → ENROLLMENT only; `patch_mini_project`/`delete_mini_project` → MINIPROJECT only. The roster cluster (0,1) and the submission cluster (2,3) never intersect in one request, so no cross-cluster cycle exists.

**Same-namespace multi-key path — `delete_run`.** One path takes *several* keys within a single namespace: `delete_run` acquires `MINIPROJECT(mp_id)` for **every** mini-project of the run (§5.5). It acquires them in **ascending `mp_id` order**, and it is the **only** multi-`MINIPROJECT` holder — `create_submission`, `patch_mini_project`, and `delete_mini_project` each hold exactly **one** `MINIPROJECT` key — so no two paths can hold-and-wait on `MINIPROJECT` keys in opposite orders (two `delete_run`s act on disjoint runs, hence disjoint key sets). No same-namespace cycle exists.

**Advisory-before-index in every enrollment path.** Every enrollment entry point acquires `ENROLLMENT(course_id)` **before** `get_or_create_user` (§5.2), so the `users.email` unique-index insert always sits *inside* the advisory lock. Ordering it the other way in only some paths (advisory *after* the index insert) would let two entry points enrolling the same brand-new email into one course cycle advisory-vs-index (`40P01`) — the Critical codex caught; the reorder removes it. This closes the **same-course** cross-endpoint case; a **cross-course, single-user** collision (same new email into two courses) is only a one-directional wait (one insert holds the `email` index, the other blocks then recovers via SAVEPOINT — no cycle, since one user is one index key).

**Email-ordering for batch `users`-table writes (replaces the round-2 global lock).** The remaining users-index hazard is **cross-course multi-user batches**: `add_students_batch` and `enroll_batch` insert *and* update several global `users` rows per transaction, under only a **course-keyed** `ENROLLMENT` lock — which does not serialize two *different-course* batches. Processed in *input* order, two such batches with overlapping brand-new emails in opposite order (A: `[x,y]`; B: `[y,x]`) form an index-vs-index cycle (A holds `x` waits `y`; B holds `y` waits `x` → `40P01`). This is pre-existing (inherent to multi-user inserts in one transaction) and orthogonal to the four invariants, but it contradicts deadlock-freedom. **Fix:** both batch endpoints perform their `users`-table writes — the new-email INSERT (via `get_or_create_user`) and the `full_name` UPDATE — in a **stable normalized-email order** (§5.3), so any two batches acquire the shared `users` index/row locks in one global order. Whoever writes the lowest email first, the other blocks on that single key holding nothing the first needs → a one-directional wait, never a cycle. This needs **no global lock**: unrelated (different-course) batches run concurrently, same-course batches already serialize on `ENROLLMENT`, and single-user paths (`add_student`, `enroll_student`) take at most one `users` write so cannot form a 2-cycle regardless. (The round-2 `USER_BATCH` singleton is dropped: it serialized *all* batches globally — every batch waited on every other — whereas email-ordering makes only batches that actually *share* a user wait, and only on that shared key.) **Email-ordering removes the deadlock, not the timeout backstop.** The batch holds its `ENROLLMENT`/`CAPACITY` advisory locks *and* the earliest user index/row locks until its single final commit (§3.3), so this one-directional wait can still exceed `statement_timeout` if the holding batch runs >30 s → the **shared `57014` backstop** every lock in this design carries (§3.3), which email-ordering does *not* eliminate — the `MAX_BATCH_SIZE` cap keeps the hold short so it stays rare.

**No advisory-vs-row-lock ordering hazard:** no advisory-locked site takes `FOR UPDATE`, and every site that takes both an advisory lock and a `MiniProject` row write (`create_submission`'s `first_submitted_at` UPDATE, `patch_mini_project`, `delete_mini_project`, and `delete_run`'s cascade/explicit `MiniProject` deletes) acquires the advisory lock(s) **before** the row write. The one `FOR UPDATE` in the tree — `publish_mini_project`'s `.with_for_update()` on the `MiniProject` row, `mini_projects.py:301` — takes **no** advisory lock, so it can never be part of an advisory wait-for cycle; it contends with `create_submission`/patch/delete only on that single `MiniProject` row lock, which yields a linear (never cyclic) wait. Deadlock-freedom is by construction; §6 proves the order is load-bearing via a deliberate order-reversal test.

### 3.3 Correctness dependencies & honest cost

- **READ COMMITTED required — and now pinned explicitly:** after a blocked waiter acquires the lock, its *next* statement (the conflict re-check / capacity `count` / re-fetched `mp` / `first_submitted_at` re-read) takes a fresh snapshot seeing the winner's committed rows. Under REPEATABLE READ the re-check would read stale. The app previously relied on this being the Postgres server default, but a role- or database-level `default_transaction_isolation` could silently promote every session to REPEATABLE READ and break the re-read. **Set `isolation_level="READ COMMITTED"` explicitly on the app engine (`database.py`) and the concurrency-test engine (Task 1)** so the guarantee is independent of server/role/db defaults; §6 asserts `SHOW transaction_isolation` returns `read committed` on a fresh connection.
- **`MINIPROJECT` is class-wide — so the critical section must be I/O-free.** `MINIPROJECT(mp_id)` is keyed on the mini-project, so **every group** submitting to it serializes on one key; during a deadline rush the whole class contends on the mini-project that just hit its deadline. Because a blocked `pg_advisory_xact_lock` acquire is itself a statement, it is bounded by `statement_timeout=30000` (`database.py:23`; no `lock_timeout` is set) — a wait exceeding 30 s would raise `QueryCanceled` (a 500). To keep the class-wide tail far under that, the ≤20 MB file read + PDF validation + temp-file write are done **before** acquiring the locks (§5.4); the locked region is DB-only (gate → `max()+1` → insert → `first_submitted_at` UPDATE → `os.replace` → commit), so each holder's critical section is ~commit latency, not ~40 MB of I/O. With that shrink, N groups × ~commit-latency stays well under 30 s at class scale. (A bounded `lock_timeout` to convert saturation into a retryable response was considered but omitted — it would add an error surface, §4; the shrunk region makes it unnecessary.)
- **Batch hold is bounded by the size cap — the `57014` backstop applies, kept rare.** Email-ordering (§3.2) drops the *global* serialization but **not** the lock holds: the batch keeps its `ENROLLMENT` (+`CAPACITY`) advisory locks and each user's index/row lock (flushed at `helpers.py:72`) until the **single** commit (`run_roster.py:242`/`enrollment.py:108`). So a contending request — a different-course batch sharing the winner's lowest email, or a same-course request on `ENROLLMENT` — waits until the whole batch commits, and that wait is bounded by `statement_timeout=30000`: a batch running >30 s makes the waiter's statement raise `QueryCanceled`/`57014` — the **same** backstop this section's `MINIPROJECT` bullet carries. The request schemas were **unbounded** (`schemas.py:258`/`:531`, `min_length=1` only); **cap both at `MAX_BATCH_SIZE = 300`** (the top of the stated class scale — the user expects ≤100–300; larger enrolments are split into chunks). A ≤300-row batch commits in a few seconds, keeping the hold well under 30 s so the `57014` stays **rare (not impossible)** — the same "keep the hold short" discipline the `MINIPROJECT` bullet applies. The cap is therefore a **modest concurrency bound *and* a UX/resource guardrail**, not merely cosmetic. Oversized batches are rejected up front with a `422` ("Batch too large (max 300); split into smaller chunks") — **input validation** (§4), not a new concurrency surface (the `57014` is pre-existing infra shared by every lock).
- **No Alembic migration** — every lock is a runtime construct; no schema change.

## 4. Error semantics — no new concurrency surface (one input-validation 422)

Holding the lock across read→write makes the **existing** guard atomic — **no new *concurrency* messages, codes, or shapes** (the slice's one addition is an input-validation `422` for oversized batches, last bullet), and (per §3.2) **no `deadlock detected` 500s**:
- #1 capacity → existing `409 "Group capacity reached"` (bulk keeps `error_code: capacity_reached`).
- #2 enrollment — **two enforcement styles, one 409 source.** The conflict **409** (`student_already_active_in_course`) is surfaced **only** by the callers on the **RunStudent** layer: `add_student` and `publish_run` return `JSONResponse(409, make_already_active_409_body(...))` (`run_roster.py:101`, `runs.py:253`), and `add_students_batch` reports the same `error_code` as a per-row error entry under its **207 Multi-Status** (`run_roster.py:205-211`). `enroll_user_in_run`'s only `HTTPException(409)` is `"Group capacity reached"` (helpers.py:198 — domain **#1**). The **StudentEnrollment** layer (`enroll_student`/`enroll_batch` → `_enroll_user`, `enrollment.py:15-61`) **raises nothing** — it enforces single-active by *deactivating* other active rows then inserting/reactivating; the lock merely makes that deactivate-then-insert atomic. That leg has **no error surface** and is verified by row-state (§6), not a 409.
- #3 submission → existing `409 "Previous submission pending evaluation"` (`submissions.py:85`) or `"Already accepted; no further submission"` (`:74-75`); `submission_number` stays accurate → the dead retry is removed (§5.4).
- #5 mini-project → existing `409 "Mini-project is locked (has submissions); use ?force=true"` (`mini_projects.py:218`) + course-admin escalation on force (`:219-222`); the lock closes the read-then-act window so the gate can no longer be bypassed. `delete_run`'s non-force path keeps its existing `409 "Run has submissions; use ?force=true to override"` (`runs.py:140`), now made atomic by holding the run's `MINIPROJECT` locks across the `has_submissions` re-check (§5.5) — no new surface.
- **batch size** → the one **new** response the slice adds: a `422 "Batch too large (max 300); split into smaller chunks"` when a batch exceeds `MAX_BATCH_SIZE` (§3.3). It is **input validation** — rejected before any lock or DB write — not a concurrency error surface. Deadlock-freedom comes from email-ordering (§3.2), not the cap; the cap additionally keeps the batch's lock-hold short so the **shared `statement_timeout` `57014` backstop** (§3.3) — which a contending batch/enroll can hit while the batch holds its locks to the single commit — stays **rare**. That `57014` is the pre-existing infrastructural timeout every lock in this design shares (§3.3), **not** a new concurrency surface or new code; and there is still no `deadlock detected` 500.

Lock release on every exit is airtight: `get_db` (`database.py:33-38`) closes the session in `finally`, rolling back → all advisory locks freed on every `raise` / `return JSONResponse` / commit (reinforced by the pool's default `reset_on_return='rollback'`).

### 5.3 batch — `add_students_batch` / `enroll_batch` (roster locks + email-ordered user writes)
Acquire, once, up front, before the per-row loop, in §3.2 order: `add_students_batch` → `ENROLLMENT(course_id)` then `CAPACITY(run_id)`; `enroll_batch` → `ENROLLMENT(course_id)`. **Up-front acquisition of the roster locks is load-bearing:** advisory-xact locks acquired *before* the per-row `db.begin_nested()` savepoints survive `ROLLBACK TO SAVEPOINT`, so a failed row cannot drop the batch's locks — whereas a lock acquired *inside* a rolled-back subtransaction **is** released (hence the helper's per-row `CAPACITY` re-acquire is a harmless re-entrant no-op, **not** the batch's real hold — both empirically confirmed on PG17). (Because the up-front `CAPACITY` acquire — not the per-row re-acquire — is the real hold, it carries its **own** wiring assertion, §6.)

**Email-order the per-row user writes (deadlock-freedom without a global lock, §3.2).** The batch's `users`-table writes — the new-email INSERT (`get_or_create_user`, `run_roster.py:196`) and the `full_name` UPDATE (`:216-217`) — are the cross-batch deadlock surface, so **process `data.rows` in a stable normalized-email order** (sort by the same normalized email string `get_or_create_user` keys on) rather than input order, so any two batches acquire the shared `users` index/row locks in one global order and cannot cycle. **Each row's internal sequence is unchanged** — `find_student_active_conflicts` still runs *before* any `full_name` mutation (`:198-217`), so a conflicting row still never mutates user state — only the order in which rows are visited changes. **Restore the 207 `results` list to input order** before returning (tag each row with its input index; sort a copy for processing; emit results ordered by input index) so the response shape is unchanged. Group assignment is by the row-supplied group *name* (`:219-229`), not processing order, so which group a student joins is unaffected; the only order-sensitive outcome is which of two rows contending for a group's last capacity slot gets the `409` — an acceptable, still-deterministic tie-break (by email rather than input position). The `rows` list is capped at `MAX_BATCH_SIZE = 300` (§3.3 — keeping the batch's lock-hold short so the shared `statement_timeout` `57014` backstop stays rare, and bounding request size; likewise `enroll_batch`'s `emails`); an oversized batch is rejected with a `422` before any lock. Then run the existing per-row loop (its `begin_nested()` SAVEPOINTs + 207 reporting) unchanged in structure. `get_or_create_user` (called at `:196`, outside the per-row savepoint) is now SAVEPOINT-safe (§3.1), so its recovery no longer rolls back the batch.

**`enroll_batch` (`enrollment.py:92-111`) likewise, simpler:** its `unique_emails` (already normalized+deduped via `dict.fromkeys(e.strip().lower())`, `:102`) is **sorted** before the `get_or_create_user`/`_enroll_user` loop (`:104-107`), with the response list restored to input order. Its `StudentEnrollment` writes are all same-course under `ENROLLMENT`, so only the `users` INSERT is the cross-batch surface email-ordering must serialize (it has no groups or `full_name` update).

### 5.4 pending-submission + submission_number — `advisory_xact_lock(db, LOCK_NS_SUBMISSION, mp_id, group_id)`
**Do the file work first, then lock.** Move the ≤20 MB `file.file.read()` + extension/PDF validation (`submissions.py:106-123`) **and** the temp-file write (`mkstemp` + `fdopen`/write; the `os.replace` stays under the lock) to **before** lock acquisition, so no 20 MB I/O runs under a lock (§3.3). Then acquire `MINIPROJECT(mp_id)` (§5.5) then `SUBMISSION(mp_id, group_id)`, **re-fetch `mp` under the lock** (below), and run the gates under both locks: the pending gate (`_latest_evaluation_result` + `prior_sub`, `submissions.py:73-92`) → deadline gates → `max(submission_number)+1` (`:127`) → build final filename → insert → `first_submitted_at` UPDATE (§5.5) → `os.replace(tmp, final)` → commit.

**Re-fetch `mp` under `MINIPROJECT` (required — closes the stale-read hole).** `mp` is loaded at `submissions.py:60`, and the deadline gates read `mp.hard_deadline`/`soft_deadline`/`resubmission_deadline` (`:94-104`) off that object. Without a refresh, a concurrent `patch_mini_project` (shortening a deadline under `MINIPROJECT`, §5.5) or `delete_mini_project` commits while `create_submission` still holds the *stale* pre-lock snapshot — so the lock protects nothing on the submit side. After acquiring `MINIPROJECT`, re-read with `mp = db.get(MiniProject, mp_id, populate_existing=True)`; if it is now `None` (a delete committed in the window), raise the same `404` `get_or_404` would have, rather than inserting a `Submission` with a now-dangling FK. All downstream gates then read the fresh row. (`run.id` is stable — a mini-project never changes runs — so only `mp` needs refreshing; the pre-lock visibility/group checks are not part of invariant #5 and stay pre-lock.)

**Guaranteed temp-file cleanup + preserved file-error 500 (required — do not omit).** Because the temp file is now written *before* the under-lock gates, every gate/deadline `409`/`404` between the write and `os.replace` would otherwise orphan a ≤20 MB `.upload-*.tmp` in the **persistent** `submission_storage_dir` — there is no sweeper, `get_db`'s `finally` frees the lock but not the file, and the pending-gate 409 (`:85`, co-submitters racing) is the highest-frequency deadline-rush rejection, so orphans accumulate unbounded on the exact hot path this slice targets. (Pre-reorder this could not happen — the temp file was written last, after all gates.) The reorder also means the file-error handler can no longer be the current single broad `except Exception` (`submissions.py:229-236`) spanning the whole region: with the gates now *inside* that region, a broad catch would mask a gate `HTTPException` (409/404) as a `500`. So **narrow the file-error catch to the I/O operations only** — the pre-lock write and the under-lock `os.replace` — each translating `OSError` to the existing `500 "Failed to write submission to disk"` (`:236`), and wrap the whole region in a `try/finally` that unlinks the orphan via the `tmp_path=None` sentinel:

```python
abs_dir = submission_storage_dir(run.id, group.id)
tmp_path: str | None = None
try:
    try:                                       # file work BEFORE the locks — no I/O under a lock
        os.makedirs(abs_dir, exist_ok=True)
        fd, tmp_path = tempfile.mkstemp(dir=abs_dir, prefix=".upload-", suffix=".tmp")
        with os.fdopen(fd, "wb") as f:
            f.write(content)
    except OSError:
        raise HTTPException(500, "Failed to write submission to disk")
    advisory_xact_lock(db, LOCK_NS_MINIPROJECT, mp_id)
    advisory_xact_lock(db, LOCK_NS_SUBMISSION, mp_id, group.id)
    mp = db.get(MiniProject, mp_id, populate_existing=True)   # refresh under the lock
    if mp is None:
        raise HTTPException(404, "Mini-project not found")
    # ...pending gate / deadline gates (fresh mp) / max()+1 / build filename / insert / first_submitted_at UPDATE...
    abs_path = os.path.join(abs_dir, filename)               # final name computed under the lock
    try:
        os.replace(tmp_path, abs_path); tmp_path = None
    except OSError:
        raise HTTPException(500, "Failed to write submission to disk")
    db.commit()
finally:
    if tmp_path is not None and os.path.exists(tmp_path):
        try: os.remove(tmp_path)
        except OSError: pass
```
Keep the `mkstemp`+write **inside** the `try` so a pre-lock write failure (e.g. ENOSPC) is caught and cleaned — preserving the coverage the current broad handler gives, without letting the narrowed `except OSError` swallow a gate result. Gate `HTTPException`s (409/404) propagate untouched through both `except OSError` blocks and hit the `finally`, which unlinks the orphan; `get_db`'s `finally` then rolls back the uncommitted DB work and frees the locks (§4). A successful `os.replace` nulls the sentinel so the `finally` is a no-op; on a reject the unlink is a single sub-ms metadata `os.remove` that runs *before* `get_db` rolls back the locks — negligibly extending only the reject-path hold (same order as the `os.replace` already accepted under the lock), never the 20 MB I/O the reorder moved out. (Reading+writing the file before the gate means a gate-rejected request has done that I/O; that waste is the price of a short class-wide hold — acceptable.)

**Delete the dead retry:** remove the `except IntegrityError` handler at `submissions.py:152-173` and collapse `try: db.flush()` (`:150-151`) to a bare `db.flush()` (the lock makes the collision unreachable; without the lock, deletion alone would turn a collision into a 500 — they land together).

### 5.5 mini-project lifecycle lock — `advisory_xact_lock(db, LOCK_NS_MINIPROJECT, mp_id)`
Serialize the atomic `first_submitted_at` *setter* against its unlocked *readers*:
- `create_submission`: acquire `MINIPROJECT(mp_id)` first (before `SUBMISSION`, §3.2), held across the `first_submitted_at` conditional UPDATE (`submissions.py:176-180`) through commit — with the file I/O already done (§5.4), the hold is DB-only; re-fetch `mp` under this lock (§5.4) so the deadline gates and existence check read the fresh row.
- `patch_mini_project` (`mini_projects.py:~154`): acquire `MINIPROJECT(mp_id)` after authz, then **re-fetch the whole entity** — `mp = db.get(MiniProject, mp_id, populate_existing=True)`, `404` if `None` (a concurrent delete committed) — and derive **all** decisions from the refreshed instance: the `locked` flag (`:158`), the *old* deadline values the extension guard compares against (`:164-172`), and `soft_changed` (`:176`). Re-reading **only** `first_submitted_at` is insufficient — the extension guard compares `new` against `getattr(mp, field)` (`:166`, the stale pre-lock deadline), so two PATCHes both loading `D0` let the second shorten a deadline the first already extended: A extends `D0→D2`, B (stale `D0`) proposes `D1` with `D0<D1<D2`, the stale `new<=old` compare against `D0` accepts it → the committed `D2` is shortened to `D1`. The full re-fetch also avoids mutating a deleted ORM instance → 500.
- `delete_mini_project` (`mini_projects.py:~214`): acquire `MINIPROJECT(mp_id)` after authz, then **re-fetch the whole entity** (`populate_existing=True`, `404` if `None`) and derive `is_locked` from it (`:216`) — closing the window where the non-force path skipped the course-admin escalation (`:217-222`) and avoiding a stale/deleted-instance read.
- `delete_run` (`runs.py:123`, **covered — the 12th site**): after authz (`require_course_admin_for_run`, `:131`) and **before** the `force` branch, load the run's mini-project ids (`SELECT id … WHERE run_id=:run ORDER BY id`) and acquire `MINIPROJECT(mp_id)` for **each, in ascending `mp_id` order** (§3.2). Holding every mini-project's lock blocks any `create_submission` from committing a first submission to the run mid-delete, so the non-force `has_submissions` re-check (`:139`) is atomic: A either sees the committed submission and returns the clean `409 "use ?force=true"`, or deletes a genuinely empty run. **On the non-force path the FKs already protect the data** — without the lock, if a submit commits in the `:139`→`:142` window, A's `db.delete(run)` cascades to the run's groups (`Run.groups` `cascade="all, delete-orphan"`, `models.py:208`; `Group.run_id` `ON DELETE CASCADE`, `:234`) and that group delete is *rejected* by the new submission's `group_id` `ON DELETE RESTRICT` (`:307`) → FK `23503`, the transaction rolls back, and run/mini-project/submission/file all survive — so the lock's non-force value is **error-quality** (a clean `409`/`404` instead of that raw `23503` 500), not preventing data loss. Taking the locks before the branch also covers the **force** cascade (`:148-171`), where the value *is* data-integrity: a concurrent `create_submission` blocks on `MINIPROJECT` and, after the force delete commits, its `mp` re-fetch (§5.4) returns `404` — instead of either phantom-succeeding (a `Submission` committed just before the force cascade deletes it via `MiniProject→Submission ON DELETE CASCADE`, `:306` — the student got a 200 for a vanished submission, possibly with an orphan file) or inserting against a force-deleted mini-project and hitting FK `23503`. A run with zero mini-projects acquires nothing and has no submissions — safe. (A mini-project *created* concurrently by `create_mini_project` racing this delete is a separate admin-structure race, deferred §8.)
  - **Reachability (both races are real).** `create_submission` checks visibility + submitter-group **only once**, up front (`submissions.py:60-70`), and never re-checks `run.is_published` or roster membership under the lock. So an **in-flight** submission that already passed those checks can commit even after the run is unpublished and its roster cleared — no re-publish/re-enroll needed. **Non-force path:** an in-flight submit committing in the `has_submissions`→`db.delete(run)` window (`:139→:142`) leaves A's `db.delete(run)` to cascade to the run's **groups** (`Run.groups` `cascade="all, delete-orphan"`, `models.py:208`; `Group.run_id` `ON DELETE CASCADE`, `:234`), and that group delete is **rejected** by the new submission's `group_id` `ON DELETE RESTRICT` (`:307`) → FK `23503`; A's transaction **rolls back**, so nothing is deleted — run, mini-project, submission row, and file all remain intact (**no orphan, no loss** — the `RESTRICT` FK is the backstop) and A simply returns an unhandled 500. **Force path:** the force branch *explicitly* deletes existing submissions (`:153-154`) before the mini-projects, so a stale in-flight submit **inserting after the force cascade committed** hits FK `23503` (its `mini_project_id` no longer exists) → an unhandled 500 (a submit committing *mid-cascade* can instead be cascade-deleted via `MiniProject→Submission ON DELETE CASCADE`, `:306`, after already returning 200). The up-front `MINIPROJECT` locks close **both**: the concurrent submit blocks, then re-fetches `mp` → `404` (or, if it committed first, non-force correctly returns `409`). §6 tests both paths.

## 6. Testing

**Concurrency fixture (Task 1)** — its **own dedicated `Engine`** with `poolclass=NullPool` (fails fast instead of masking a leak behind `pool_timeout`), **never** the app `SessionLocal` (pool `5+5=10`; N>10 mutually-blocked threads would exhaust it). Build it with the **same `connect_args`** as the app engine (`options: "-c statement_timeout=30000 -c TimeZone=UTC"`, `database.py:23`) so a mis-authored worker that blocks on `pg_advisory_xact_lock` is bounded by `statement_timeout` instead of hanging CI, and keeps timezone parity — **and the same `isolation_level="READ COMMITTED"`** (§3.3) so the post-lock re-reads behave as in production. Yields N `Session`s on separate real connections. Teardown, in order: **(1) join/await all worker threads (with a bounded timeout that fails loudly, not an unbounded join)** (SQLAlchemy `Session`s are not thread-safe, and a still-blocked worker holds `ACCESS SHARE` that would fail the autouse TRUNCATE after its 5 s `lock_timeout`); **(2) `rollback()`+`close()` each worker session; (3) `engine.dispose()`** — all **before** the autouse `_isolation` TRUNCATE (declare the fixture dependent on `_isolation` for LIFO). On NullPool, `close()`+`dispose()` physically close the DBAPI connections (releasing locks server-side); the `rollback()` is a defensive belt and the **thread-join** is the load-bearing step. One test: a worker raising mid-critical-section still leaves the DB truncatable.

**Forced-interleave seam** — each critical section gets a test-only monkeypatchable no-op hook **between the guard-read and the write**. **Engage the blocking seam ONLY in the lock-removed RED fail-first.** In the lock-PRESENT (GREEN) run the seam is a plain no-op; the test proves the fix by an arrangement that is **deterministic** for that invariant (below) — never by hoping a free-running race lands a particular way. (Engaging a blocking seam under the lock would deadlock: the lock precedes the seam, so a blocked thread never reaches its seam while the winner parks at the seam holding the lock.)

**Per-invariant fail-first + GREEN arrangement:**
- **#1 capacity — symmetric.** RED: two threads add distinct users to a 9-member group; both pass the count check at the seam; release both → 11 members (`RunStudent` unique is `(run_id,user_id)`, no insert collision masks it). GREEN: free-running race → exactly one 409, count stays ≤10 (outcome deterministic regardless of winner).
- **#2 RunStudent — symmetric.** RED: two threads add the *same* student to two different runs of one course; both `find_student_active_conflicts` empty at the seam; release both → active in two runs. GREEN: one wins, the other 409s. **New-email variant (proves the bypass fix, §5.2):** two threads add the same *brand-new* email into two runs of one course — pre-reorder both resolve `existing_user=None` (`run_roster.py:77`) and skip the conflict check entirely (`:80`), so the seam never fires and both enroll; the get_or_create-first reorder routes both through the lock + check. RED (no lock) → two active; GREEN → one 409. This is a distinct interleave from the pre-existing-student RED above and gets its own fail-first.
- **#2 StudentEnrollment — count-based, at `_enroll_user` level, GREEN must wrap the lock.** Call `_enroll_user` directly with **two distinct versions** of one course (endpoints can't — they resolve the same newest version, `UNIQUE(user_id,version_id)`-guarded). RED: no lock, seam-driven interleave → **2 active rows**. GREEN: wrap each thread's `_enroll_user` in `advisory_xact_lock(db, LOCK_NS_ENROLLMENT, course_id)` (mimicking the production caller — `_enroll_user` itself holds no lock) → natural serialization → **1 active row**. Assert the active-row **count**, not a 409.
- **#3 pending-submission — asymmetric.** RED: hold thread B at a seam **after the pending-gate (`~:85`) but before `max()+1` (`:127`)** (the `86-126` region is a valid seam location); let thread A run to a **full commit** of submission #1; then release B → B's fresh READ COMMITTED snapshot reads A's row, computes `max+1=2`, inserts a second **pending** row (no `UNIQUE` collision) → 2 pending. (A symmetric release would collide on `submission_number` and leave 1 pending — a false fail-first.) GREEN: B blocks on `SUBMISSION`, re-reads after A commits → 409.
- **#5 mini-project — asymmetric in operation, GREEN must be sequenced.** RED: thread A = `delete_mini_project` (non-force, run-teacher not course-admin) reads `is_locked=False` at the seam; thread B = `create_submission` commits `first_submitted_at`; release A → A deletes the now-locked mini-project + files without escalation (bypass). GREEN: **run B (submit) to full commit, then launch A (delete)** → A acquires `MINIPROJECT`, re-reads `is_locked=True`, hits the `force`/course-admin gate. (A free-running GREEN race is non-deterministic — A-wins-lock would legally delete the not-yet-locked mini-project — so the GREEN arrangement is sequenced, not raced.)
- **#5 stale-`mp` on the submit side (Finding 2) — asymmetric, sequenced GREEN.** RED (no refresh): thread B = `patch_mini_project` shortens `hard_deadline` to the past and commits under `MINIPROJECT`; thread A = `create_submission` was constructed with the *pre-shorten* `mp` snapshot (loaded at `:60`) and, reading that stale deadline, accepts the submission past the new deadline. (A `delete_mini_project` variant → A inserts a `Submission` against the deleted mini-project → FK error / 500.) GREEN: **run B to full commit, then launch A** → A acquires `MINIPROJECT`, re-fetches `mp` (`populate_existing=True`), reads the shortened deadline → `409` (or, for the delete variant, `mp is None` → `404`). Asserts the fresh read governs, not the `:60` snapshot.
- **#5 `delete_run` — both paths reachable via an in-flight submit (§5.5), deterministic.** `create_submission` passes visibility/group once up front (`submissions.py:60-70`), so hold thread B (submit) at a seam **after** those checks. **Non-force RED (FK `23503`, rollback leaves everything intact):** with B parked, unpublish the run + clear its roster (so non-force `delete_run` passes `:134`/`:137`); thread A = `delete_run` non-force parks after `has_submissions=False` (`:139`); release B → B `os.replace`s its file and commits its row (which references its group with `ON DELETE RESTRICT`); release A → `db.delete(run); db.commit()` cascades to the run's groups (`models.py:208`/`:234`) and is **rejected** by B's submission's `group_id` `RESTRICT` (`:307`) → assert A raises an unhandled **FK `23503`** 500 **and** its transaction rolled back: run, mini-project, submission row, and file are **all still present** (no orphan, no loss). Non-force GREEN: A acquires the run's `MINIPROJECT` locks first; B blocks on `MINIPROJECT(mp)`; A re-reads `has_submissions=False` → deletes the still-empty run → commits → releases; B unblocks, re-fetches `mp` → `None` → `404`; assert A returns `204`, B `404`s, **no 500, no orphan**. **Force RED (FK `23503`):** thread A = `delete_run` force runs its cascade to a **full commit** (mini-projects gone); then release B → B attempts its `Submission` insert with the now-dangling `mini_project_id` → assert FK **`23503`** 500. Force GREEN: A (force) acquires the `MINIPROJECT` locks and parks holding them; B blocks on `MINIPROJECT(mp)`; release A → force-cascade commits + releases; B unblocks, re-fetches `mp` → `None` → `404`; assert A returns `204`, no orphan, B `404`s. (Blocking GREENs — the lock *blocks* B until the delete commits.)
- **#5 `patch_mini_project` deadline lost-update (Finding 4) — symmetric, two-PATCH.** RED (re-read only `first_submitted_at`, not the whole entity): a locked mini-project has `hard_deadline = D0`; two PATCHes both load `D0` at the seam; A extends to `D2` and commits; release B → B's extension guard compares its proposed `D1` (`D0<D1<D2`) against its **stale** `D0` (`mini_projects.py:166`), passes (`D1>D0`), and commits → the deadline is shortened from `D2` to `D1`, violating "can only be extended." GREEN: B blocks on `MINIPROJECT`, re-fetches the whole entity (`populate_existing`) → sees `D2`, compares `D1<=D2` → `409 "… can only be extended (new must be > old)"`. Asserts the extension guard's *old* value comes from the fresh row, not the `:154` snapshot.

**Layer-1 primitive proof (deterministic):** per domain, session A holds the advisory lock, session B's `SELECT pg_try_advisory_xact_lock(:k)` returns `false`; A commits → B's retry returns `true`. (No `NOWAIT` form of the blocking acquire exists; `pg_try_*` is the primitive.)

**Isolation-level pin proof (Finding 4):** a deterministic single-connection test asserts `SHOW transaction_isolation` returns `read committed` on a fresh **app-engine** connection (and on the concurrency-fixture engine), so the post-lock re-reads' correctness dependency (§3.3) is guarded against a server/role/db `default_transaction_isolation` override.

**Wiring + ordering assertions — at EVERY locked site.** Spy/monkeypatch `advisory_xact_lock` and assert the expected `(namespace, *ids)` **and** that the call is recorded **before** that site's guard-read (instrument the guard-read — the `count`/`find_student_active_conflicts`/`_latest_evaluation_result`/`first_submitted_at`/`has_submissions` read, or the `get_or_create_user` insert — and assert ordering; single-threaded, cheap, so it verifies lock *position* everywhere, which wiring alone cannot). Cover all **13 acquisitions across 11 fixed-arity sites, plus `delete_run` (a 12th site, variable-arity `MINIPROJECT`)**: `enroll_user_in_run`, `patch_student` move, `bulk_move` (CAPACITY); `add_student` (ENROLLMENT — asserted **before `get_or_create_user`**), `add_students_batch` (**ENROLLMENT and CAPACITY** — assert ENROLLMENT before CAPACITY, both before the row loop), `enroll_student` (ENROLLMENT), `enroll_batch` (ENROLLMENT, before the loop) — each enrollment path asserted **before `get_or_create_user`**, and both batch endpoints separately asserted (single-threaded) to visit their `users`-table writes in sorted-email order (§5.3); `publish_run` (ENROLLMENT); `create_submission` (**MINIPROJECT and SUBMISSION** — plus the `mp` re-fetch asserted *after* `MINIPROJECT` and *before* the deadline gates, Finding 2); `patch_mini_project`, `delete_mini_project` (MINIPROJECT — each with the **whole-entity `populate_existing` re-fetch** asserted after the lock and before the guard reads, Finding 4); `delete_run` (**one `MINIPROJECT` per run mini-project, ascending `mp_id`** — assert the acquires precede the `has_submissions` read at `:139`). Each raceable site also gets a forced-interleave test — including `patch_mini_project` (the two-PATCH deadline lost-update, Finding 4) and the capacity movers; `publish_run`'s readiness gate is explicitly documented as position-verified-by-ordering-assertion only (no thread race).

**Deadlock regression (non-vacuous):** because every path shares one order, two real paths can't cycle — so the test **monkeypatches one site to reverse its order** and races it against `add_student`. It uses a **between-acquisitions barrier** (park each thread holding its first lock before requesting its second) — hang-free because the two paths take *disjoint* first locks (ENR vs CAP), so neither blocks the other's first acquire — then releases both and asserts `DeadlockDetected` surfaces. The **control** run ("patch removed, both complete") runs the two correct-order paths **without** the barrier — a plain concurrent run that serializes and both complete; reusing the strict two-party barrier there would hang (both take ENROLLMENT first, so one blocks on its first acquire and never reaches the barrier). (The guard-read seam sits after both acquisitions on `add_student`, so it can't drive the reversed case — a dedicated between-acquisitions barrier is required.)

**Cross-endpoint advisory-vs-index deadlock (Finding 1 — distinct from the namespace-reversal test above).** The reversal test only exercises advisory-vs-advisory ordering; the enrollment Critical is advisory-vs-*unique-index*, so it needs its own test. Race `add_student` (correct order: `ENROLLMENT` → `get_or_create_user`) against `enroll_student` enrolling the **same brand-new email** into the **same course**, with `enroll_student` forced (monkeypatch) to the rev-6 buggy order (`get_or_create_user` → `ENROLLMENT`). Arrange: park `enroll_student` **after** its `users` insert (holding the uncommitted `email` index) but **before** its `ENROLLMENT` acquire; let `add_student` take `ENROLLMENT(course)` then attempt its own `users` insert → it blocks on the parked index row; release `enroll_student` → it requests `ENROLLMENT(course)` and blocks on `add_student` → **assert `DeadlockDetected` (`40P01`)**. Then the shipped-order control (both paths `ENROLLMENT`-before-`get_or_create_user`): both serialize and **both complete** — `add_student` writes a `RunStudent`, `enroll_student` writes a `StudentEnrollment`, and since `find_student_active_conflicts` (`helpers.py:641`) checks **only `RunStudent`** it finds no conflict against the sibling's `StudentEnrollment`, so neither 409s. Assert: no deadlock, exactly **one `User`** row (one insert won, the other resolved via SAVEPOINT), one active `RunStudent`, one active `StudentEnrollment`. (Do **not** expect a roster 409 — the two endpoints enforce invariant #2 on *different* tables.) This is the fail-first that proves the reordering is load-bearing, not cosmetic.

**Cross-course batch deadlock (Finding 3 — the email-ordering proof).** Race two `add_students_batch` calls on **different courses** with overlapping brand-new emails in **opposite input order** (course A rows `[x, y]`, course B rows `[y, x]`), each parked at a between-users seam (after inserting its first new user, before its second). RED (input-order processing, monkeypatch off the email sort): A holds `x`'s index and waits on `y`; B holds `y`'s index and waits on `x` → **`DeadlockDetected` (`40P01`)** for one batch. GREEN (email-ordered processing, §5.3): both batches visit the shared emails in the **same** sorted order (`x` then `y`), so whoever inserts `x` first, the other blocks on `x` holding nothing the first needs → a one-directional wait; both complete and exactly one `User` exists per email. Asserts email-ordering removes the cross-course index cycle the course-keyed `ENROLLMENT` lock cannot — **with no global lock**. (A same-course pair needs no email-ordering: both take `ENROLLMENT(course)` and serialize outright.)

**Batch-size cap + shared timeout backstop (§3.3/§4).** A schema test asserts a `301`-row/`301`-email batch is rejected with `422` before any lock or DB write. A deterministic contention test (concurrency engine, deliberately **low** `statement_timeout`) **documents** the shared `57014` backstop on the batch path: batch A parks mid-loop holding its `ENROLLMENT` lock + the just-flushed index lock of a shared user; a contending same-course request (or a different-course batch sharing A's lowest email) blocks on that lock and is canceled at the low timeout → `57014`, surfacing as the same infrastructural `statement_timeout` 500 every lock in this design shares (§3.3). Documents that email-ordering removes the **deadlock** (`40P01`) but not the timeout-500, which the `MAX_BATCH_SIZE = 300` cap keeps **rare (not impossible)** by bounding the hold — it does **not** prove unreachability.

**Off-HTTP semantics & fabrication:** thread bodies call the router/service functions directly with per-thread sessions. Handlers **raise `HTTPException`** (`enroll_user_in_run` capacity, `create_submission`, `patch_mini_project`, `delete_mini_project`) or **return `JSONResponse(409)`** (`add_student` conflict) — assert `status_code`, not an HTTP response; `_enroll_user` neither raises nor returns a 409 (assert row-count). `create_submission` takes a bare `UploadFile` → each thread fabricates a `starlette.datastructures.UploadFile` over a `SpooledTemporaryFile` of `%PDF-` bytes.

Task 1 lands the fixture + seam + wiring/ordering helper + one real fail-first (the #3 asymmetric protocol) to de-risk the approach early — no threading/advisory precedent exists in the suite.
