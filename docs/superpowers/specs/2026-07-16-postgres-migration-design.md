# Postgres Migration (Phase 9-A1) — Design

**Status:** Draft (awaiting user review)
**Date:** 2026-07-16
**Scope:** Backend + dev/test infrastructure only. Frontend untouched.

## Context

Mathion runs on SQLite today (`create_engine("sqlite:///./mathion.db")`; tests on in-memory SQLite). Phase 9-A (concurrency hardening) requires PostgreSQL — the race fixes are `SELECT ... FOR UPDATE` / advisory locks / SAVEPOINT-retry, which SQLite cannot express (it serializes all writes behind one global write lock). Postgres is also the intended production database for an LMS whose real workload is concurrent writes (a class of up to ~200 students, ≤10 per group, submitting near a deadline).

Decision (locked with the user): **move Mathion entirely to PostgreSQL — dev, test, and production — and drop SQLite support completely.** Rejected alternatives: "keep both" (divergence tax; SQLite tests mask Postgres behavior — the exact masking that motivated this) and "SQLite in production" (single-writer lock is wrong for the submission-rush workload, and it makes the concurrency slice moot).

Phase 9-A decomposes into two independently shippable slices:
- **A1 — Postgres migration (THIS spec):** app + tests + dev on Postgres, one clean initial migration, full suite green. No locking changes.
- **A2 — Concurrency hardening (next slice):** the ~13 race sites fixed and verified with real concurrency tests on Postgres.

## Goal

The application, the full test suite (currently 1058 passed / 1 skipped), and local development all run on PostgreSQL. SQLite is removed from the codebase. Production is configured via a single `MATHION_DATABASE_URL` env var (works for managed hosts *and* self-hosted Postgres). Deliverable is standalone: nothing about locking changes here.

## Non-goals

- **Concurrency / locking fixes** — that is A2. A1 must not change any read-then-write or capacity logic.
- **Choosing a production host.** Config is `MATHION_DATABASE_URL`-driven; hosting (Neon / Supabase / Railway / Render / Fly / self-hosted) is decided later.
- **Data migration.** Production is not live and dev data is disposable (seed scripts). Fresh database + `alembic upgrade head` + reseed. No migration of existing rows.
- **Frontend changes.** None.

## Locked decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Databases | Postgres for dev + test + prod; drop SQLite | Concurrency correctness + prod target; no divergence tax |
| Driver | **psycopg3** (`psycopg[binary]`), `postgresql+psycopg://` | Actively developed; one package family for dev (binary) and self-hosted prod; SQLAlchemy 2.0-recommended. Replaces the incidental `psycopg2-binary`. |
| Postgres version | **17** (current stable) for dev/CI | Newest stable; `MATHION_DATABASE_URL` lets any host override |
| Prod config | `MATHION_DATABASE_URL` env var only | Portable across managed + self-hosted |
| Migrations | **Reset**: delete the 16 SQLite-era migrations, replace with ONE autogenerated Postgres-native initial migration | No data to preserve; drops `batch_alter_table` shims + one-time SQLite data-backfills; simpler to trust |
| Test schema | Built by running the real migration(s) (`alembic upgrade head`) once per session | Guarantees test schema == prod schema; drift impossible |
| Test isolation | `TRUNCATE ... RESTART IDENTITY CASCADE` between tests | Real commit semantics like prod; **won't fight A2's app-level SAVEPOINTs / row locks** the way a savepoint-rollback harness would |

## Architecture / components

### 1. Dependencies (`backend/pyproject.toml`)
- Add `psycopg[binary]` (psycopg3). Remove `psycopg2-binary` if declared.
- SQLAlchemy 2.0.49, Alembic 1.18.4, FastAPI 0.136, uvicorn 0.44 unchanged.

### 2. Configuration & engine
- `config.py` (`Settings`, `env_prefix="MATHION_"`): the `database_url` field **defaults to the local docker Postgres URL** (`postgresql+psycopg://mathion:mathion@localhost:5432/mathion`) for zero-config dev, and is overridden by `MATHION_DATABASE_URL` in test/prod. **No SQLite default, no SQLite fallback.**
- `database.py`:
  - Engine gains production-grade pool settings: `pool_pre_ping=True` (survive dropped connections), a modest `pool_size` + `max_overflow` (concrete values chosen in the plan).
  - **Delete `enable_sqlite_fk`** and its `PRAGMA foreign_keys=ON` listener — Postgres enforces foreign keys natively.
- No SQLite branch remains anywhere in app code.

### 3. Local dev provisioning
- `docker-compose.yml` at repo root: a `postgres:17` service with a named volume, a healthcheck, and env for db/user/password.
- `.env.example` documenting `MATHION_DATABASE_URL` (and the test URL).
- Bootstrap becomes: `docker compose up -d db` → `alembic upgrade head` → `python -m scripts.seed_*`. Documented in the README/runbook.

### 4. Migration reset (single Postgres-native initial migration)
The models (`Base.metadata`) are the source of truth — the test suite already builds from them via `create_all` and passes, so models == current effective schema. Procedure:
1. Stand up a fresh Postgres; delete the 16 files under `alembic/versions/`.
2. `alembic revision --autogenerate -m "initial schema"` from the models against the empty Postgres.
3. **Review the generated migration carefully** (the one real risk point). Checklist:
   - `DateTime(timezone=True)` → `TIMESTAMP WITH TIME ZONE` (real tz semantics; SQLite ignored this).
   - `Numeric(20,10)` (quiz `correct_numeric`) preserved.
   - `server_default=func.now()` / `server_default="0"` — present (they are model-declared, so autogenerate should capture them; verify each).
   - Named `CheckConstraint`s (e.g. `ck_evaluation_result_enum`) present — statuses are `String(20)` + CHECK, **not** native enums, so no PG `ENUM` type is created (intended).
   - All indexes, `UniqueConstraint`s, and FK `ondelete` rules (e.g. `Submission.group_id` RESTRICT) match the models.
4. That migration is base + head. `alembic upgrade head` provisions prod and the test schema.
5. One-time data-backfill logic from the old chain (`info_html` backfill, Phase-7c UserItemState recompute, tz conversion) is intentionally dropped — it fixed data that will not exist on a fresh database.

Old migration files remain in git history for archaeology.

### 5. Test harness redesign (`backend/tests/conftest.py`)
Current: module-level in-memory SQLite engine (`StaticPool`, `check_same_thread`), `create_all`/`drop_all` per test (autouse `setup_db`), `db` fixture = session on that engine, `client` overrides `get_db` to yield the **same** `db` session (app and test share one session — load-bearing for tests like `_assert_hidden` and unpublish-then-GET).

Target (preserves the shared-session semantics exactly; only schema-build + isolation change):
- **Session-scoped:** connect to a dedicated **test database** (`MATHION_TEST_DATABASE_URL`, defaulting to a `mathion_test` database on the local instance); run `alembic upgrade head` once to build the schema. conftest reads this env var directly (it is not part of the app `Settings`).
- **Function-scoped isolation:** after each test, `TRUNCATE <all model tables> RESTART IDENTITY CASCADE` (leaving `alembic_version` intact). Table list from `Base.metadata.sorted_tables`.
- Keep `db` (real session, real commits) and `client` (`get_db` override yielding that session) semantically identical — individual tests need no changes.
- Remove SQLite-only bits (`StaticPool`, `check_same_thread`, the SQLite pragma listener).
- The recently added `db.rollback()` in `test_patch_evaluation_as_admin_succeeds` behaves naturally: the endpoint's real commit already persisted, so rollback is a no-op for committed data — same as production.

Test-DB provisioning for CI: a `postgres:17` service container + `MATHION_TEST_DATABASE_URL`. (Parallel test workers via pytest-xdist would need one database per worker — out of scope now; noted for later.)

### 6. Seed scripts
- `scripts/seed_*.py` verified to run against Postgres (they use the ORM, so expected to be portable; any SQLite-ism fixed in-slice).

## Data flow: bootstrap
- **Dev:** `docker compose up -d db` → `alembic upgrade head` → seed → `uvicorn`.
- **Test:** session fixture → `alembic upgrade head` on the test DB → run tests (truncate between) → done.
- **Prod:** set `MATHION_DATABASE_URL` → `alembic upgrade head` → run. No data import.

## Error handling / edge cases (Postgres strictness)
Postgres is stricter than SQLite's flexible typing; the migration may surface **latent** bugs, which are good catches and fixed in-slice:
- **tz-naive datetimes** written to `TIMESTAMPTZ` columns — Postgres is exacting where SQLite stored strings. Code already moved toward `to_utc_aware`; any remaining naive write may error or warn.
- **Boolean / integer coercion** — Postgres will reject a string where a boolean/int is expected; SQLite silently accepted it.
- **Case / `ORDER BY` / NULL-ordering** differences in a query a test pins.
These are expected to be few and small; the plan budgets a fix pass.

## Testing strategy & success criteria
1. **Full suite green on Postgres** — the existing 1058 tests pass against the PG harness (any failures are latent typing/tz bugs, fixed in-slice, not suppressed).
2. **Migrations apply clean** on a fresh Postgres (`alembic upgrade head` from empty).
3. **No schema drift** — a test asserting `alembic revision --autogenerate` produces an **empty** diff against the migrated schema (models == migration == test schema).
4. **One-command local bootstrap** — `docker compose up -d db` + documented steps bring up a working dev environment; a seed script runs on PG.
5. SQLite is absent from app + test code (grep-clean).

## Risks & rollout
- **Conftest redesign touches load-bearing fixtures.** Mitigation: preserve the exact shared-session behavior; change only schema-build + isolation. This is the highest-attention part of the slice and gets the strict per-task review.
- **Autogenerated initial migration is imperfect.** Mitigation: the explicit review checklist (§4.3) + the no-drift test (success criterion 3).
- **Latent Postgres-strictness bugs.** Mitigation: budgeted fix pass; each fix is a real bug caught, not a regression introduced.
- **Rollback:** the branch is revertable wholesale before merge; nothing is deployed.
