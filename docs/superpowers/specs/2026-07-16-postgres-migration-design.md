# Postgres Migration (Phase 9-A1) — Design

**Status:** Draft — revised after two 5-reviewer rounds (awaiting user review)
**Date:** 2026-07-16
**Scope:** Backend + dev/test infrastructure only. Frontend untouched.

## Context

Mathion runs on SQLite today (`create_engine("sqlite:///./mathion.db")`; tests on in-memory SQLite). Phase 9-A (concurrency hardening) requires PostgreSQL — the race fixes are `SELECT ... FOR UPDATE` / advisory locks / SAVEPOINT-retry, which SQLite cannot express (it serializes all writes behind one global write lock). Postgres is also the intended production database for an LMS whose real workload is concurrent writes (a class of up to ~200 students, ≤10 per group, submitting near a deadline).

Decision (locked with the user): **move Mathion entirely to PostgreSQL — dev, test, and production — and drop SQLite support completely.** Rejected alternatives: "keep both" (divergence tax; SQLite tests mask Postgres behavior — the exact masking that motivated this) and "SQLite in production" (single-writer lock is wrong for the submission-rush workload, and it makes the concurrency slice moot).

Phase 9-A decomposes into two independently shippable slices:
- **A1 — Postgres migration (THIS spec):** app + tests + dev on Postgres, one clean initial migration, full suite green. No locking changes.
- **A2 — Concurrency hardening (next slice):** the ~13 race sites fixed and verified with real concurrency tests on Postgres.

## Goal

The application, the full test suite, and local development all run on PostgreSQL. SQLite is removed from the codebase. Production is configured via a single `MATHION_DATABASE_URL` env var (works for managed hosts *and* self-hosted Postgres). Deliverable is standalone: nothing about locking changes here.

## Non-goals

- **Concurrency / locking fixes** — that is A2. A1 must not change any read-then-write or capacity logic. (One narrow exception: adding a deterministic `ORDER BY` to currently-unordered list queries — see §7 — is a portability fix, not a locking change.)
- **Choosing a production host.** Config is `MATHION_DATABASE_URL`-driven; hosting (Neon / Supabase / Railway / Render / Fly / self-hosted) is decided later.
- **Data migration.** Production is not live and dev data is disposable (seed scripts). Fresh database + `alembic upgrade head` + reseed. No migration of existing rows.
- **Frontend changes.** None.

## Locked decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Databases | Postgres for dev + test + prod; drop SQLite | Concurrency correctness + prod target; no divergence tax |
| Driver | **psycopg3** (`psycopg[binary]`), `postgresql+psycopg://` | Actively developed; one package family for dev (binary) and self-hosted prod; SQLAlchemy 2.0-recommended. Replaces the incidental `psycopg2-binary`. Self-hosted prod *may* later prefer `psycopg[c]` (compiled against system libpq); noted, not required for A1. |
| Postgres version | **17** (current stable) for dev/CI | Newest stable; `MATHION_DATABASE_URL` lets any host override |
| Prod config | `MATHION_DATABASE_URL` env var only | Portable across managed + self-hosted |
| Migrations | **Reset**: delete the 16 SQLite-era migrations, replace with ONE autogenerated Postgres-native initial migration | No data to preserve; drops `batch_alter_table` shims + one-time SQLite data-backfills; simpler to trust |
| Test schema | Built by running the real migration(s) (`alembic upgrade head`) once per session | Guarantees test schema == prod schema; drift impossible |
| Test isolation | `TRUNCATE ... RESTART IDENTITY CASCADE` between tests | Real commit semantics like prod; **won't fight A2's app-level SAVEPOINTs / row locks** the way a savepoint-rollback harness would |
| Test DB wiring | **One engine**: the test process **assigns** `MATHION_DATABASE_URL` = the test DB (a *distinct* `mathion_test` database) *before* importing `mathion.config`; app + harness share `mathion.database.engine` | Avoids a dual-engine hazard where app code that opens its own `SessionLocal()` (dispatcher, CLI) targets a *different* DB than the harness built (see §5). Plain assignment (not `setdefault`) + a distinct DB name are load-bearing safety rails (see §5) |

## Architecture / components

### 1. Dependencies (`backend/pyproject.toml`)
- Add `psycopg[binary]` (psycopg3). Remove `psycopg2-binary` (currently at `pyproject.toml:13`; incidentally installed, imported nowhere in app/test/script code — verified).
- SQLAlchemy 2.0.49, Alembic 1.18.4, FastAPI 0.136, uvicorn 0.44 unchanged.

### 2. Configuration & engine
- `config.py` (`Settings`, `env_prefix="MATHION_"` → the field maps to `MATHION_DATABASE_URL`): the `database_url` field **defaults to the local docker Postgres URL** (`postgresql+psycopg://mathion:mathion@localhost:5432/mathion`) for zero-config dev, and is overridden by `MATHION_DATABASE_URL` in test/prod. **No SQLite default, no SQLite fallback.**
- **Prod localhost-default footgun:** a prod deploy that forgets `MATHION_DATABASE_URL` silently targets `localhost`. It fails loud (connection refused) rather than corrupting data, but to match the existing "insecure dev default" warnings (`secret_key`, `cookie_secure`): on startup, log one line echoing the **password-redacted** target host/db, and document `MATHION_DATABASE_URL` as required-in-prod in the runbook.
- `database.py`:
  - Engine gains production-grade pool settings: `pool_pre_ping=True` (survive dropped connections), `pool_recycle` (e.g. 300–1800 s, for hosts/proxies that reap idle connections), a modest `pool_size` + `max_overflow`, and `connect_args={"connect_timeout": …}` (fail fast on a dead DB). Concrete values chosen in the plan and sized against the worker model (§8). SSL for managed hosts is **URL-driven** (`?sslmode=require`) — do not add a redundant `connect_args` for it.
  - **Delete `enable_sqlite_fk`** (`database.py:22-33`) and its `PRAGMA foreign_keys=ON` listener — Postgres enforces foreign keys (incl. the models' `ondelete` CASCADE/RESTRICT/SET NULL) natively and unconditionally.
- No SQLite branch remains anywhere in app code. (Verified: `database.py:22-33` is the only SQLite branch in app code; `config.py:9` default is the only other SQLite reference.)

### 3. Local dev provisioning
- `docker-compose.yml` at repo root: a `postgres:17` service with a named volume, a healthcheck, and env for db/user/password.
- `.env.example` documenting `MATHION_DATABASE_URL` (and the test URL). **Note:** `Settings.model_config` sets only `env_prefix`, no `env_file`, so the app process does **not** auto-load `.env` — docker-compose reads `.env` for *its own* interpolation, but a host-run `uvicorn`/`alembic` sees only the shell environment. The plan will either add `env_file=".env"` to `model_config` **or** state in the runbook that `.env` is for compose/`export` only. (Post-migration, this matters: unlike today, the default is a *Postgres* URL, so a dev who relies on `.env` for a non-default host must `export` it.)
- Bootstrap becomes: `docker compose up -d --wait db` → `alembic upgrade head` → `python -m scripts.seed_*`. The `--wait` gates on the healthcheck so a host-run `alembic upgrade` cannot race a not-yet-ready container (a healthcheck alone only gates *other compose services'* `depends_on`, not a host process). Documented in the README/runbook.
- **Update the existing dev scripts** (they *are* the runbook and currently assume SQLite): `run-debug.sh` (bare `uvicorn --reload`, no DB provisioning) and `run-dashboards-smoke.sh:24-28` (`rm -f mathion.db` + `alembic upgrade head`). Rewrite to the `docker compose up -d --wait db` flow. (`run-dashboards-smoke.sh` is currently untracked; the plan touches it explicitly.)

### 4. Migration reset (single Postgres-native initial migration)
The models (`Base.metadata`) are the source of truth for the reset: we **regenerate the migration FROM the models**, so migration == models by construction, and the fresh-DB schema is defined by the models. (Nuance, not a blocker: several columns carry a model-level Python `default=` with **no** `server_default` — `mini_projects.is_published`, `submissions.is_late`/`is_resubmission`, `course_versions.label`, `blocks.info_html`, and the two `is_disabled` columns at models_auth.py:16 / models.py:43. These are safe because the app inserts exclusively via the ORM, which applies `default=` on INSERT. Old SQLite-era migrations carried extra `server_default`s the models omit — e.g. `label server_default=''`, `info_html server_default=''`; the reset intentionally drops those. So the accurate framing is "new migration == models," **not** "models == old effective schema.")

The **one** boolean column that carries a literal `server_default` is `Group.is_disabled` (models.py:236, `server_default="0"`); it is normalized to `sa.text("false")` (§4a). No other `is_disabled` gets that change.

All 27 tables are registered on `Base.metadata` when `alembic/env.py` imports the two model modules (importing the module executes it and registers every mapped class, regardless of env.py's partial `from … import (names)` list — verified: `SuperuserPanelToken` and `NotificationLogEntry` register despite being absent from the name lists) — so `--autogenerate` sees every table.

Procedure:
1. Stand up a fresh Postgres (driver + docker PG must land first); delete the 16 files under `alembic/versions/`.
2. `alembic revision --autogenerate -m "initial schema"` from the models against the empty Postgres.
3. **Review the generated migration carefully** (the one real risk point). A `create_table` block renders `server_default`, `CheckConstraint`, `UniqueConstraint`, `Index`, and FK `ondelete` regardless of any `compare_*` flag, so the migration *content* is complete; this checklist confirms it:
   - `DateTime(timezone=True)` → `TIMESTAMP WITH TIME ZONE` (real tz semantics; SQLite ignored this).
   - `Numeric(20,10)` (quiz `correct_numeric`, models.py:136) preserved.
   - `server_default=func.now()` on the 31 timestamp columns present (22 in models.py + 9 in models_auth.py).
   - `server_default`: `retry_count` (Integer, models_auth.py:112) and the normalized `is_disabled` (`sa.text("false")`, models.py:236) present.
   - Named `CheckConstraint`s (`ck_evaluation_result_enum`, `ck_mini_project_*`, `ck_submission_*`, `ck_evaluation_*`) present — statuses are `String(20)` + CHECK, **not** native enums, so no PG `ENUM` type is created (verified: no `Enum()` column anywhere).
   - **JSON columns** (`last_answers` models_auth.py:96 nullable, `payload` :109 non-null) render as PG `json` (text-preserving, not `JSONB`).
   - All indexes (incl. `evaluations.submission_id` `unique=True`, models.py:338), `UniqueConstraint`s, and FK `ondelete` rules (e.g. `Submission.group_id` RESTRICT, `RunAsset.uploaded_by` SET NULL) match the models. (Note: the old migrations' explicitly-named FKs — `fk_*` — become PG-default names `<table>_<col>_fkey`; zero behavioral impact, no code references FK names. See §Open items for the A2 `naming_convention` follow-up.)
4. That migration is base + head. `alembic upgrade head` provisions prod and the test schema.
5. One-time data-backfill logic from the old chain (`info_html` backfill, Phase-7c UserItemState recompute, tz conversion) is intentionally dropped — it fixed data that will not exist on a fresh database.

Old migration files remain in git history for archaeology.

### 4a. Alembic drift configuration (`alembic/env.py`)
`env.py:28` unconditionally sets `sqlalchemy.url` from `settings.database_url`, and its online `context.configure()` (line 50) sets **neither** `compare_type` nor `compare_server_default`. Two changes:
- **URL:** no code change needed *if* the test process assigns `MATHION_DATABASE_URL` before import (§5) — `settings.database_url` then already points at the test DB, so env.py's clobber is correct whether alembic runs in-process (same imported `settings`) or as a subprocess (inherits the env). The app config remains the single source of the URL; we do **not** add a second var that env.py wouldn't see.
- **Comparison flags:** set `compare_type=True` and `compare_server_default=True` explicitly in the **online** `context.configure()` (env.py:50). This governs the **CLI** `alembic revision --autogenerate` and any future drift-check path; it is what stops a real server-default drift from being silently missed. (Do not rely on Alembic's defaults for these — pin both. Setting them in the *offline* `configure()` is inert, since autogenerate/`compare_metadata` only run online; leave offline unchanged.) The criterion-3 no-drift *test* (§4b) does **not** depend on these env.py flags — it builds its own `MigrationContext` with the same flags.

### 4b. No-drift verification (success criterion 3)
The no-drift test builds a `MigrationContext` with `compare_type=True` + `compare_server_default=True` and asserts `compare_metadata(context, Base.metadata)` returns an **empty** diff (in-process, via `alembic.autogenerate.compare_metadata` — *not* by shelling out `alembic revision --autogenerate`, which would write a stray file). To keep the gate deterministic:
- The one known phantom-diff source (`is_disabled` boolean `"0"` vs PG `false`) is removed by normalizing the model `server_default` to `sa.text("false")` (§4a).
- The reset *helps* the `func.now()` columns: the old migrations used `sa.text('(CURRENT_TIMESTAMP)')` (a SQLite-ism) which would phantom-diff against `func.now()` models on PG; regenerating renders `now()`, which reflects and compares cleanly.
- **Explicitly verify-during-tuning** (do not assume clean): `is_disabled` (post-normalization) and `retry_count` (Integer `"0"` — Alembic's PG impl should strip the cast so `'0'::integer` == `'0'`, but confirm live). §4b budgets for tuning any residual autogenerate false-positives (function-default text, implicit indexes) until the diff is genuinely empty — this tuning is explicit, not assumed-zero.

### 5. Test harness redesign (`backend/tests/conftest.py`)
Current: a **separate** module-level in-memory SQLite engine (`test_engine`, `StaticPool`, `check_same_thread`), `create_all`/`drop_all` per test (autouse `setup_db`), `db` fixture = session on `test_engine`, `client` overrides `get_db` to yield the **same** `db` session (app and test share one session — load-bearing for tests like `_assert_hidden` and unpublish-then-GET). Critically, `test_engine` is *not* the app's `mathion.database.engine`.

**Dual-engine hazard (must fix, not inherit):** `mathion.database.engine`/`SessionLocal` bind to `settings.database_url` at import. `get_db`'s override only redirects the *request* path. But `SessionLocal()` is also opened directly by the notification dispatcher loop (`dispatcher.py:215`) and the superuser CLI (`superuser/__main__.py:20`). One test — `test_notifications_lifespan.py::test_lifespan_shutdown_with_inflight_tick` — starts the **real** lifespan (`email_mode="memory"`) and drives `run_forever → _do_tick → SessionLocal()` against `settings.database_url`. (The `test_notifications_lock.py` cases do **not** reach the tick path: one raises at lock acquisition before `run_forever`, the other runs `email_mode="disabled"`.) On SQLite this quietly hit a stray `./mathion.db` and read zero rows; on Postgres that same path would hit the **dev** DB or, if none is reachable, raise `OperationalError` (swallowed → green for the wrong reason).

Target (preserves the shared-session semantics exactly; unifies onto one engine):
- **Env-var-before-import, by ASSIGNMENT:** at the very top of `conftest.py` (alongside the existing `os.environ.setdefault("MATHION_EMAIL_MODE", …)` at conftest.py:10-12), **assign** (do **not** `setdefault`) `os.environ["MATHION_DATABASE_URL"]` = the test DB URL *before* importing `mathion.config`/`mathion.database`. The URL comes from a dedicated `MATHION_TEST_DATABASE_URL` (CI-overridable), defaulting to a **distinct** `mathion_test` database on the local instance. Assignment (not `setdefault`) is a **data-loss guardrail**: the harness runs `DROP SCHEMA public CASCADE` + per-test `TRUNCATE`, so it must *never* inherit a dev/prod `MATHION_DATABASE_URL` a developer happens to have exported — it forces the test DB unconditionally. (This differs deliberately from the email-mode `setdefault`, whose worst case — the wrong mailer — is harmless; here the worst case is a wiped dev database.)
- **`pytest_configure` guard (runs at collection, before any fixture):** assert `settings.database_url` **equals the concrete test URL** and that its database name is the dedicated `*_test` name (≠ the dev default `mathion`). This exact-match guard is the last rail before the destructive schema ops; a mis-pointed URL aborts the run instead of dropping data. (Mirrors the existing email-mode `pytest_configure` assertion.)
- **One engine:** delete conftest's separate `test_engine`/`TestSession`; the `db` fixture opens a session on `mathion.database.engine` (`SessionLocal`). `client` continues to override `get_db` to yield that same session. Individual tests need no changes.
- **Session-scoped schema build (`autouse`, session-scoped; a dependency of `db`/the truncate fixture so no connection is checked out before the schema exists):** ensure the test database exists — connect with AUTOCOMMIT to the server's maintenance DB (`postgres`; the connecting role needs `CREATEDB`, satisfied by the docker/CI `postgres` superuser), check `pg_database` / catch `DuplicateDatabase`, `CREATE DATABASE mathion_test` if absent — then reset it to a pristine schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public`; requires the test role to **own** the test DB, true when the maintenance connection created it as the same `mathion` user — note for self-hosted CI with a non-owner role) and run `alembic upgrade head`. The DROP-SCHEMA reset makes the session robust to a stale schema left by a prior run on old revisions.
- **Function-scoped isolation:** after each test, close the session, then `TRUNCATE <all model tables> RESTART IDENTITY CASCADE` in a single statement (leaving `alembic_version` intact — not a model table). Table list from `Base.metadata.sorted_tables`. Truncation runs *after* the session is closed so no open transaction holds locks. (Verified: no test asserts a specific autoincrement id or relies on cross-test id state — the only literal ids are the intentional-nonexistent `99999`/`999999` — so `RESTART IDENTITY` is safe.)
- Remove SQLite-only bits (`StaticPool`, `check_same_thread`, the pragma listener at conftest.py:69-73).
- The `db.rollback()` in `test_patch_evaluation_as_admin_succeeds` behaves naturally: the endpoint's real commit already persisted, so rollback is a no-op for committed data — same as production.
- **Concurrency note (for the plan / step-0 run):** under one engine, `test_lifespan_shutdown_with_inflight_tick` now runs the dispatcher on a **real second connection** concurrently with the test (previously serialized on in-memory SQLite), and — with real committed rows — becomes a *meaningful* mid-batch-shutdown test that still only asserts "no leaked task." The lifespan `__aexit__` drain completes before teardown, so `_do_tick`'s connection returns to the pool before the teardown `TRUNCATE`. Confirm at step 0 that this specific test doesn't hang; if a drain-timeout ever left a tick mid-transaction, teardown `TRUNCATE ... CASCADE` would block on its lock. Low probability, worth an explicit watch line.

**CI provisioning:** a `postgres:17` service container; the same assign-env-var + session-fixture create/reset path runs unchanged. Parallel workers via pytest-xdist would need one DB per worker — out of scope now.

### 6. Seed scripts
- `scripts/seed_*.py` are all ORM-only (no raw SQL, no `text()`, no `PRAGMA`, no `.db` paths, no `lastrowid`/autoincrement reliance) and open `SessionLocal` from `mathion.database` — verified portable; they bind to PG post-migration and run unchanged. Any SQLite-ism that surfaces is fixed in-slice.

### 7. Query portability fixes (SQLite → Postgres ordering)
SQLite returned rows in rowid order absent `ORDER BY`; Postgres guarantees no order. One genuine bug plus a **complete** single-key-sort tie-break sweep:
- **Unordered pagination (real bug):** `api/courses.py:45` and `:65` (`select(Course).offset().limit()` with no `ORDER BY`) become non-deterministic across pages on PG. Add `.order_by(Course.id)`. (`courses.py` is the only paginated outlier — `blocks.py`, `items.py`, `versions.py` all order before paging.)
- **Unordered roster list:** `api/enrollment.py:118` returns a `StudentEnrollment` list to the UI unordered — add a stable key. (`courses.py` + `enrollment.py` are the only two *fully* order-by-less multi-row endpoints — all 21 `response_model=list[...]` endpoints were swept.)
- **Single-key sorts on non-unique / transaction-time columns (tie-break sweep — add a secondary `.id`):**
  - `func.now()` `created_at`/`submitted_at` sorts, which are the **most** tie-prone on PG because `now()` returns the *transaction start time* — every row committed in one transaction gets an identical value: `run_roster.py:120`, `dashboard.py:161`, `run_teachers.py:62` (all `created_at`), `submissions.py:252`/`:264` (`submitted_at`).
  - Non-unique text/date sorts: `runs.py:69` (`Run.start_date`), `groups.py:44` (`Group.name`), `assets.py:117` / `run_assets.py:222` (`filename`). (These three text sorts are partly protected by unique constraints, so they tie rarely — lower priority than the `created_at` group.)
  - Mirror the already-correct pattern: `dispatcher.py:106` (`created_at.asc(), id.asc()`), `versions.py:199-201` (`created_at.desc(), id.desc()`).
- This is the "ordering-sweep acceptance check" of criterion 6 — sweep **all** single-key list sorts, not only the named ones.

### 8. Worker / connection-pool sizing
SQLAlchemy's default `QueuePool` allows up to `pool_size (5) + max_overflow (10)` = 15 connections **per process**; managed hosts cap connections low (tens). The plan states the assumed worker model and sizes the pool to `pool_size × workers + max_overflow × workers ≤ host max_connections`. The notification dispatcher's singleton flock (`dispatcher.py:21-45`, `acquire_singleton_lock` → `RuntimeError` on the second holder, acquired at `main.py:53-54` only when email is enabled) effectively forces **one** uvicorn worker whenever email is on — so the realistic A1 target is single-worker; the budget formula still governs the email-disabled multi-worker case. Deferred to deploy-time/A2 (named so they aren't dropped): transaction-mode poolers (PgBouncer / Supabase pooler) break psycopg3's default server-side prepared statements → need `prepare_threshold=None` or session mode; and a server-side `statement_timeout` (to stop a runaway query pinning a scarce connection) — `lock_timeout` proper belongs to A2's locking work.

## Data flow: bootstrap
- **Dev:** `docker compose up -d --wait db` → `alembic upgrade head` → seed → `uvicorn`.
- **Test:** session fixture (ensure DB exists → DROP/CREATE schema → `alembic upgrade head`) → run tests (TRUNCATE between) → done.
- **Prod:** set `MATHION_DATABASE_URL` → `alembic upgrade head` (explicit deploy step, not app-boot autorun) → run. No data import.

## Error handling / edge cases (Postgres strictness)
Postgres is stricter than SQLite's flexible typing. **Some fallout is knowable now, not merely "latent"** — the plan enumerates and fixes these specifically, and additionally budgets a fix pass for anything the step-0 full-suite run surfaces:
- **Tests that baked in SQLite's tz-stripping and now invert:** `test_notifications_dispatcher.py:230-232` asserts `next_attempt_at == (now + …).replace(tzinfo=None)` "because SQLite strips tzinfo"; under `TIMESTAMPTZ` the read-back is tz-*aware*, so the naive comparison fails. Fix: drop `.replace(tzinfo=None)` and compare aware-to-aware (`now` is already `timezone.utc`). (Grep confirms this is the only `.replace(tzinfo=None)` in the tree.)
- **In-test `PRAGMA foreign_keys=OFF` — the two files need DIFFERENT rewrites (per-FK):**
  - `test_notifications_dispatcher.py:74-85` (`test_build_render_context_missing_user_raises`) inserts a `NotificationLogEntry` with `user_id=999999` via PRAGMA-off to test the dispatcher's "referent missing: user" branch. But `NotificationLogEntry.user_id` is `ondelete="CASCADE"` + `nullable=False` (models_auth.py:107): on Postgres that row is **impossible to create** (the FK always rejects it), and the missing-user branch is **unreachable in production** (deleting the user cascade-deletes the notification row). **Fix: delete this test** — the scenario cannot exist on PG. The dispatcher branch may remain as defensive code but is untestable and should not be "fixed" by weakening the FK.
  - `test_run_assets.py:234-267` (`…uploaded_by_email_null_when_user_row_missing`) inserts a `RunAsset` with `uploaded_by=99999` via PRAGMA-off. `RunAsset.uploaded_by` is `ondelete="SET NULL"` (models.py:363). **Fix: create the asset with a real throwaway user, then hard-DELETE that user** — the `SET NULL` cascade nulls `uploaded_by`, and the endpoint returns `uploaded_by_email=None`, same assertion, exercising the real cascade. Update the docstring (its "bypassed the SET NULL cascade" premise is now moot — the cascade *is* the mechanism).
  - (Grep: `PRAGMA` in `tests/` appears only in these two files, conftest's deleted listener, and the deleted migration test.)
- **`func.now()` = transaction-start-time** (not statement/row time) on Postgres — the mechanism behind the §7 `created_at` tie-break sweep, and it means two default timestamps in one transaction are *equal* (a test asserting strict inequality between them would fail; none currently does).
- **tz-naive datetime WRITES — confirmed absent:** every `datetime.now(...)` passes `timezone.utc`; `to_utc_aware()` (`helpers.py`) and `.tzinfo is None` guards already defend the read-back transition.
- **JSON `None` (clarified, NOT a portability difference):** with the models' bare `JSON` (default `none_as_null=False`), an *explicitly-set* Python `None` persists as JSON `'null'` (not SQL NULL) — **identically on SQLite and Postgres** (type-level bind, not DB-level), so no regression. The app never assigns `None` to these columns (`last_answers` is only ever set to a dict at `quiz.py:132` or left unset; `payload` is `nullable=False`), so an *unset* nullable JSON column lands as SQL NULL. **Do not add `none_as_null=True` in A1** (that would change `WHERE … IS NULL` semantics — out of scope). The criterion-4 assertion must reflect this (see below).
- **Confirmed absent (stated so the plan doesn't chase non-issues):** case-sensitive `LIKE` (no `.like()`/`.ilike()` anywhere; `=` email lookups are exact on normalized lowercase values, case-sensitive on both engines), raw SQL outside `database.py`, `rowid`/`AUTOINCREMENT` reliance, `IntegrityError` message-string inspection (all handlers are generic 409s), boolean/integer string coercion (all boolean predicates are typed-column comparisons), `GROUP BY` strictness (all eight grouped queries list non-aggregate columns or group by a functionally-dependent PK), NULL-ordering (no `ORDER BY` targets a nullable column that can appear in its result set — `Run.start_date`/`end_date` are non-null; `helpers.py:81` orders `published_at` but filters to published rows), `DISTINCT ON`/`LIMIT` interaction, SQLite collation (`COLLATE`) reliance. The SPA static mount / asset filesystem is DB-independent; `.gitignore` already covers `*.db`.

## Testing strategy & success criteria

## Risks & rollout
- **Conftest redesign touches load-bearing fixtures + a destructive reset.** Mitigation: preserve the exact shared-session behavior; the assignment-not-`setdefault` rail + distinct `mathion_test` DB + exact-match `pytest_configure` guard make the `DROP SCHEMA`/`TRUNCATE` blast radius safe. Highest-attention part of the slice; strict per-task review.
- **Autogenerated initial migration is imperfect.** Mitigation: the §4.3 checklist, the no-drift test (criterion 3), and the independent semantic assertions (criterion 4).
- **Latent Postgres-strictness bugs.** Mitigation: the step-0 early full-suite run enumerates the real set; each fix is a real bug caught, not a regression introduced.
- **Rollback:** the branch is revertable wholesale before merge; nothing is deployed.
