# Postgres Migration (Phase 9-A1) — Design

**Status:** Draft — revised after 5-reviewer pass (awaiting user review)
**Date:** 2026-07-16
**Scope:** Backend + dev/test infrastructure only. Frontend untouched.

## Context

Mathion runs on SQLite today (`create_engine("sqlite:///./mathion.db")`; tests on in-memory SQLite). Phase 9-A (concurrency hardening) requires PostgreSQL — the race fixes are `SELECT ... FOR UPDATE` / advisory locks / SAVEPOINT-retry, which SQLite cannot express (it serializes all writes behind one global write lock). Postgres is also the intended production database for an LMS whose real workload is concurrent writes (a class of up to ~200 students, ≤10 per group, submitting near a deadline).

Decision (locked with the user): **move Mathion entirely to PostgreSQL — dev, test, and production — and drop SQLite support completely.** Rejected alternatives: "keep both" (divergence tax; SQLite tests mask Postgres behavior — the exact masking that motivated this) and "SQLite in production" (single-writer lock is wrong for the submission-rush workload, and it makes the concurrency slice moot).

Phase 9-A decomposes into two independently shippable slices:
- **A1 — Postgres migration (THIS spec):** app + tests + dev on Postgres, one clean initial migration, full suite green. No locking changes.
- **A2 — Concurrency hardening (next slice):** the ~13 race sites fixed and verified with real concurrency tests on Postgres.

## Goal

The application, the full test suite, and local development all run on PostgreSQL. SQLite is removed from the codebase. Production is configured via a single `MATHION_DATABASE_URL` env var (works for managed hosts *and* self-hosted Postgres). Deliverable is standalone: nothing about locking changes here.

## Non-goals

- **Concurrency / locking fixes** — that is A2. A1 must not change any read-then-write or capacity logic. (One narrow exception: adding a deterministic `ORDER BY` to two currently-unordered list queries — see §7 — is a portability fix, not a locking change.)
- **Choosing a production host.** Config is `MATHION_DATABASE_URL`-driven; hosting (Neon / Supabase / Railway / Render / Fly / self-hosted) is decided later.
- **Data migration.** Production is not live and dev data is disposable (seed scripts). Fresh database + `alembic upgrade head` + reseed. No migration of existing rows.
- **Frontend changes.** None.

## Locked decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Databases | Postgres for dev + test + prod; drop SQLite | Concurrency correctness + prod target; no divergence tax |
| Driver | **psycopg3** (`psycopg[binary]`), `postgresql+psycopg://` | Actively developed; one package family for dev (binary) and self-hosted prod; SQLAlchemy 2.0-recommended. Replaces the incidental `psycopg2-binary`. Self-hosted prod *may* later prefer `psycopg[c]` (compiled against system libpq); noted, not required for A1. |
| Postgres version | **17** (current stable) for dev/CI | Newest stable; `MATHION_DATABASE_URL` lets any host override |
| Prod config | `MATHION_DATABASE_URL` env var only | Portable across managed + self-hosted |
| Migrations | **Reset**: delete the 16 SQLite-era migrations, replace with ONE autogenerated Postgres-native initial migration | No data to preserve; drops `batch_alter_table` shims + one-time SQLite data-backfills; simpler to trust |
| Test schema | Built by running the real migration(s) (`alembic upgrade head`) once per session | Guarantees test schema == prod schema; drift impossible |
| Test isolation | `TRUNCATE ... RESTART IDENTITY CASCADE` between tests | Real commit semantics like prod; **won't fight A2's app-level SAVEPOINTs / row locks** the way a savepoint-rollback harness would |
| Test DB wiring | **One engine**: the test process sets `MATHION_DATABASE_URL` to the test DB *before* importing `mathion.config`; app + harness share `mathion.database.engine` | Avoids a dual-engine hazard where app code that opens its own `SessionLocal()` (dispatcher, CLI) targets a *different* DB than the harness built (see §5) |

## Architecture / components

### 1. Dependencies (`backend/pyproject.toml`)
- Add `psycopg[binary]` (psycopg3). Remove `psycopg2-binary` (currently at `pyproject.toml:13`; incidentally installed, imported nowhere in app code — verified).
- SQLAlchemy 2.0.49, Alembic 1.18.4, FastAPI 0.136, uvicorn 0.44 unchanged.

### 2. Configuration & engine
- `config.py` (`Settings`, `env_prefix="MATHION_"` → the field maps to `MATHION_DATABASE_URL`): the `database_url` field **defaults to the local docker Postgres URL** (`postgresql+psycopg://mathion:mathion@localhost:5432/mathion`) for zero-config dev, and is overridden by `MATHION_DATABASE_URL` in test/prod. **No SQLite default, no SQLite fallback.**
- **Prod localhost-default footgun:** a prod deploy that forgets `MATHION_DATABASE_URL` silently targets `localhost`. It fails loud (connection refused) rather than corrupting data, but to match the existing "insecure dev default" warnings (`secret_key`, `cookie_secure`): on startup, log one line echoing the **password-redacted** target host/db, and document `MATHION_DATABASE_URL` as required-in-prod in the runbook.
- `database.py`:
  - Engine gains production-grade pool settings: `pool_pre_ping=True` (survive dropped connections), `pool_recycle` (e.g. 300–1800 s, for hosts/proxies that reap idle connections), a modest `pool_size` + `max_overflow`, and `connect_args={"connect_timeout": …}` (fail fast on a dead DB). Concrete values chosen in the plan and sized against the worker model (see §8). SSL for managed hosts is **URL-driven** (`?sslmode=require`) — do not add a redundant `connect_args` for it.
  - **Delete `enable_sqlite_fk`** (`database.py:22-33`) and its `PRAGMA foreign_keys=ON` listener — Postgres enforces foreign keys natively and unconditionally.
- No SQLite branch remains anywhere in app code. (Verified: `database.py` is the only SQLite branch in app code; `config.py:9` default is the only other SQLite reference.)

### 3. Local dev provisioning
- `docker-compose.yml` at repo root: a `postgres:17` service with a named volume, a healthcheck, and env for db/user/password.
- `.env.example` documenting `MATHION_DATABASE_URL` (and the test URL). **Note:** `Settings.model_config` sets only `env_prefix`, no `env_file`, so the app process does **not** auto-load `.env` — docker-compose reads `.env` for *its own* interpolation, but a host-run `uvicorn`/`alembic` sees only the shell environment. The plan will either add `env_file=".env"` to `model_config` **or** state in the runbook that `.env` is for compose/`export` only. (It happens to work today only because the default already equals the localhost URL.)
- Bootstrap becomes: `docker compose up -d --wait db` → `alembic upgrade head` → `python -m scripts.seed_*`. The `--wait` gates on the healthcheck so a host-run `alembic upgrade` cannot race a not-yet-ready container (a healthcheck alone only gates *other compose services'* `depends_on`, not a host process). Documented in the README/runbook.
- **Update the existing dev scripts** (they *are* the runbook and currently assume SQLite): `run-debug.sh` (bare `uvicorn --reload`, no DB provisioning) and `run-dashboards-smoke.sh:24-27` (`rm -f mathion.db` + `alembic upgrade head`). Rewrite to the `docker compose up -d --wait db` flow. (`run-dashboards-smoke.sh` is currently untracked; the plan touches it explicitly.)

### 4. Migration reset (single Postgres-native initial migration)
The models (`Base.metadata`) are the source of truth for the reset: we **regenerate the migration FROM the models**, so migration == models by construction, and the fresh-DB schema is defined by the models. (Nuance, not a blocker: several columns carry a model-level Python `default=` with **no** `server_default` — `mini_projects.is_published`, `submissions.is_late`/`is_resubmission`, `course_versions.label`, `blocks.info_html`. These are safe because the app inserts exclusively via the ORM, which applies `default=` on INSERT. Old SQLite-era migrations may have carried extra `server_default`s the models omit; the reset intentionally drops those. Do **not** describe this as "models == old effective schema" — it isn't, exactly; it *is* "new migration == models".)

All 27 tables are registered on `Base.metadata` when `alembic/env.py` imports the two model modules (importing the module executes it and registers every mapped class, regardless of env.py's partial `from … import (names)` list) — so `--autogenerate` sees every table. No missing-table risk.

Procedure:
1. Stand up a fresh Postgres (driver + docker PG must land first); delete the 16 files under `alembic/versions/`.
2. `alembic revision --autogenerate -m "initial schema"` from the models against the empty Postgres.
3. **Review the generated migration carefully** (the one real risk point). A `create_table` block renders `server_default`, `CheckConstraint`, `UniqueConstraint`, `Index`, and FK `ondelete` regardless of any `compare_*` flag, so the migration *content* is complete; this checklist confirms it:
   - `DateTime(timezone=True)` → `TIMESTAMP WITH TIME ZONE` (real tz semantics; SQLite ignored this).
   - `Numeric(20,10)` (quiz `correct_numeric`, models.py:136) preserved.
   - `server_default=func.now()` on the ~30 timestamp columns present.
   - `server_default="0"`: `retry_count` (Integer, models_auth.py:112) and `is_disabled` (Boolean, models.py:236) present. **`is_disabled` is normalized to `sa.text("false")` in the model** (see §4a) so it round-trips as a PG boolean and doesn't produce a phantom no-drift diff; assert the boolean default reads back as `False`.
   - Named `CheckConstraint`s (`ck_evaluation_result_enum`, `ck_mini_project_*`, `ck_submission_*`, `ck_evaluation_*`) present — statuses are `String(20)` + CHECK, **not** native enums, so no PG `ENUM` type is created (intended and verified: no `Enum()` column anywhere).
   - **JSON columns** (`last_answers` models_auth.py:96, `payload` :109) render as PG `JSON` (text-preserving, not `JSONB`); confirm Python `None` maps to SQL `NULL` (not JSON `'null'`).
   - All indexes (incl. `evaluations.submission_id` `unique=True`), `UniqueConstraint`s, and FK `ondelete` rules (e.g. `Submission.group_id` RESTRICT) match the models.
4. That migration is base + head. `alembic upgrade head` provisions prod and the test schema.
5. One-time data-backfill logic from the old chain (`info_html` backfill, Phase-7c UserItemState recompute, tz conversion) is intentionally dropped — it fixed data that will not exist on a fresh database.

Old migration files remain in git history for archaeology.

### 4a. Alembic drift configuration (`alembic/env.py`)
`env.py` currently (line 28) unconditionally sets `sqlalchemy.url` from `settings.database_url`, and its online `context.configure()` (line 50) sets **neither** `compare_type` nor `compare_server_default`. Two changes:
- **URL:** no code change needed *if* the test process sets `MATHION_DATABASE_URL` before import (§5) — `settings.database_url` then already points at the test DB, and env.py's clobber becomes correct. (The app config remains the single source of the URL; we do not add a second env var that env.py wouldn't see.)
- **Comparison flags:** set `compare_type=True` (Alembic 1.18.4 default is already `True`, but pin it explicitly) **and `compare_server_default=True`** in **both** the online and offline `context.configure()` calls, so the no-drift test (criterion 3) actually inspects the `server_default`s that §4.3 cares about. Without this the gate is blind to exactly that drift.

### 4b. No-drift verification (success criterion 3, revised)
The no-drift test builds a `MigrationContext` with the **same** `compare_type=True` + `compare_server_default=True` flags and asserts `compare_metadata(context, Base.metadata)` returns an **empty** diff (in-process, via `alembic.autogenerate.compare_metadata` — *not* by shelling out `alembic revision --autogenerate`, which would write a stray file). To keep the gate deterministic:
- The one known phantom-diff source (`is_disabled` boolean `"0"` vs PG `false`) is removed by normalizing the model `server_default` to `sa.text("false")` (§4a).
- `func.now()` reflects as `now()` on Postgres and normally matches; **the plan authors this test only after the migration is final, runs it, and tunes any residual autogenerate false-positives** (function-default text, implicit indexes) until the diff is genuinely empty. This tuning is explicitly budgeted, not assumed-zero.

### 5. Test harness redesign (`backend/tests/conftest.py`)
Current: a **separate** module-level in-memory SQLite engine (`test_engine`, `StaticPool`, `check_same_thread`), `create_all`/`drop_all` per test (autouse `setup_db`), `db` fixture = session on `test_engine`, `client` overrides `get_db` to yield the **same** `db` session (app and test share one session — load-bearing for tests like `_assert_hidden` and unpublish-then-GET). Critically, `test_engine` is *not* the app's `mathion.database.engine`; the app engine (bound to `settings.database_url`) is only ever used by code that opens its own session — and that is the hazard below.

**Dual-engine hazard (must fix, not inherit):** `mathion.database.engine`/`SessionLocal` bind to `settings.database_url` at import. `get_db`'s override only redirects the *request* path. But `SessionLocal()` is also opened directly by the notification dispatcher loop (`dispatcher.py:215`) and the superuser CLI (`superuser/__main__.py:20`). Tests that start the **real** lifespan — `test_notifications_lifespan.py::test_lifespan_shutdown_with_inflight_tick`, `test_notifications_lock.py:71,95` — drive `run_forever → _do_tick → SessionLocal()` against `settings.database_url`. On SQLite this quietly hit a stray `./mathion.db` file and the tests only asserted "no leaked task." On Postgres that same path would hit the **dev** DB (wrong data / side effects) or, if no PG is reachable, raise `OperationalError` (swallowed → green for the wrong reason).

Target (preserves the shared-session semantics exactly; unifies onto one engine):
- **Env-var-before-import:** at the very top of `conftest.py` (extending the existing `os.environ.setdefault("MATHION_EMAIL_MODE", …)` at conftest.py:10-12), set `os.environ["MATHION_DATABASE_URL"]` to the test DB URL **before** importing `mathion.config`/`mathion.database`. Then `mathion.database.engine`, Alembic (via `settings.database_url`), and every direct `SessionLocal()` all target the *same* test DB. Add a `pytest_configure` assertion that `settings.database_url` is the test URL (mirrors the existing email-mode guard).
- **One engine:** delete conftest's separate `test_engine`/`TestSession`; the `db` fixture opens a session on `mathion.database.engine` (i.e. `SessionLocal`). `client` continues to override `get_db` to yield that same session. Individual tests need no changes.
- **Session-scoped schema build:** a session fixture ensures the test database exists (creating it via an autocommit **maintenance** connection to the server's default DB if absent — Postgres has no `CREATE DATABASE IF NOT EXISTS`, so check `pg_database`/catch `DuplicateDatabase`), then resets it to a pristine schema (`DROP SCHEMA public CASCADE; CREATE SCHEMA public`) and runs `alembic upgrade head`. The DROP-SCHEMA reset makes the session robust to a stale schema left by a prior run on old revisions.
- **Function-scoped isolation:** after each test, close the session, then `TRUNCATE <all model tables> RESTART IDENTITY CASCADE` in a single statement (leaving `alembic_version` intact — it is not a model table). Table list from `Base.metadata.sorted_tables` (CASCADE makes sort order irrelevant, but the list is what scopes the statement). Truncation runs *after* the session is closed so no open transaction holds locks.
- Remove SQLite-only bits (`StaticPool`, `check_same_thread`, the SQLite pragma listener at conftest.py:69-73).
- The recently added `db.rollback()` in `test_patch_evaluation_as_admin_succeeds` behaves naturally: the endpoint's real commit already persisted, so rollback is a no-op for committed data — same as production.

**Test-DB provisioning for CI:** a `postgres:17` service container; the same env-var + session-fixture create/reset path runs unchanged. Parallel test workers via pytest-xdist would need one database per worker — out of scope now; noted for later.

### 6. Seed scripts
- `scripts/seed_*.py` are all ORM-only (no raw SQL, no `text()`, no `PRAGMA`, no `.db` paths, no `lastrowid`/autoincrement reliance) — verified portable, expected to run on Postgres unchanged. Any SQLite-ism that surfaces is fixed in-slice.

### 7. Query portability fixes (SQLite → Postgres behavior)
SQLite returned rows in rowid order absent `ORDER BY`; Postgres guarantees no order. One genuine bug plus an ordering sweep:
- **Unordered pagination (real bug):** `api/courses.py:45` and `:65` (`select(Course).offset().limit()` with no `ORDER BY`) become non-deterministic across pages on PG. Add `.order_by(Course.id)`. (Every other paginated endpoint — `blocks.py`, `items.py`, `versions.py` — already orders; `courses.py` is the outlier.)
- **Unordered roster list:** `api/enrollment.py:118` returns a `StudentEnrollment` list to the UI unordered — add a stable key (e.g. `User.email` or `created_at`).
- **Unstable single-key sorts (tie-break sweep):** `runs.py:69` (`Run.start_date`), `groups.py:44` (`Group.name`), `assets.py:117` / `run_assets.py:222` (`filename`) — where a test or the UI pins exact order, add a secondary `.id` tie-break. Low severity; treated as an ordering-sweep acceptance check.

### 8. Worker / connection-pool sizing
SQLAlchemy's default `QueuePool` allows `pool_size (5) + max_overflow (10)` = up to 15 connections **per process**; managed hosts cap connections low (tens). The plan states the assumed worker model and sizes the pool to `pool_size × workers + max_overflow × workers ≤ host max_connections`. Note the notification dispatcher's singleton flock (`dispatcher.py`, `acquire_singleton_lock` raises on the second worker) effectively forces **one** uvicorn worker whenever email is enabled — so the realistic A1 target is a single-worker deployment. Transaction-mode poolers (PgBouncer / Supabase pooler) break psycopg3's default server-side prepared statements — deployments on such hosts need `prepare_threshold=None` (or the pooler's session mode); named here as a known deploy-time follow-up (hosting is out of scope).

## Data flow: bootstrap
- **Dev:** `docker compose up -d --wait db` → `alembic upgrade head` → seed → `uvicorn`.
- **Test:** session fixture (ensure DB exists → DROP/CREATE schema → `alembic upgrade head`) → run tests (TRUNCATE between) → done.
- **Prod:** set `MATHION_DATABASE_URL` → `alembic upgrade head` → run. No data import.

## Error handling / edge cases (Postgres strictness)
Postgres is stricter than SQLite's flexible typing. **Some of the fallout is knowable now, not merely "latent"** — the plan enumerates and fixes these specifically (see the test list below), and additionally budgets a fix pass for anything the early full-suite run surfaces:
- **Tests that baked in SQLite's tz-stripping and now invert:** `test_notifications_dispatcher.py:231` asserts `(now + …).replace(tzinfo=None)` "because SQLite strips tzinfo"; under `TIMESTAMPTZ` the read-back is tz-*aware*, so the naive comparison fails. Fix to compare aware values. (Grep for `.replace(tzinfo=None)` before sizing the pass — this is the only current occurrence.)
- **In-test `PRAGMA foreign_keys=OFF`:** `test_notifications_dispatcher.py:77,83` and `test_run_assets.py:248,260` toggle FK enforcement to insert a dangling-FK row (`uploaded_by=99999`). On Postgres `PRAGMA` is a no-op and FKs are always enforced → `IntegrityError`. Rewrite PG-safely (create-then-hard-delete the referenced user, or drop the dangling-row scenario). (Grep for `PRAGMA` in `tests/` — these two files plus conftest's listener and the deleted migration test are the only hits.)
- **tz-naive datetime WRITES — confirmed absent:** every `datetime.now(...)` passes `timezone.utc`; `to_utc_aware()` (`helpers.py`) and `.tzinfo is None` guards already defend the read-back transition. No naive-write bug expected.
- **Confirmed absent (stated so the plan doesn't chase non-issues):** case-sensitive `LIKE` (no `.like()`/`.ilike()` anywhere; email lookups are exact `==` on normalized values), raw SQL / SQLite functions outside `database.py`, `rowid`/`AUTOINCREMENT` reliance, `IntegrityError` message-string inspection (all handlers are generic 409s), boolean/integer string coercion (all boolean filters are typed-column comparisons), `GROUP BY` strictness (every aggregate lists non-aggregate columns or groups by a functionally-dependent PK). The SPA static mount / asset filesystem is DB-independent; `.gitignore` already covers `*.db`.

## Testing strategy & success criteria
0. **Run the full suite EARLY** — stand up the minimal PG conftest (env-var wiring + session schema build + truncate) *first*, run the whole suite before polishing fixtures, and record the actual failure set. This measures the slice instead of guessing it. Known failures to expect: the deleted migration-round-trip file (criterion 1), the PRAGMA-FK-off tests, the inverted tz assertion.
1. **Full suite green on Postgres** — the existing suite passes against the PG harness. **The baseline count changes**: `test_notifications_migration.py` is **deleted** (it hardcodes `sqlite:///` URLs, `PRAGMA table_info`, and up/down round-trips against the now-deleted revisions `2f3e694d3544`/`378c62a02d4e`, and asserts a to-be-deleted migration uses `batch_alter_table` — none of which can survive or be "fixed in-slice"; its round-trip coverage is intentionally obsoleted by the single-migration reset). The plan records the new baseline after the step-0 run. Any remaining failures are real typing/tz bugs fixed in-slice, not suppressed.
2. **Migrations apply clean** on a fresh Postgres (`alembic upgrade head` from empty).
3. **No schema drift** — a test asserting `compare_metadata` (with `compare_type=True` + `compare_server_default=True`, in-process) produces an **empty** diff against the migrated schema (models == migration == test schema). See §4b.
4. **Semantic schema assertions** — a reflection-based test confirms the migration actually produced: `TIMESTAMPTZ` on the tz columns, `Numeric(20,10)` on `correct_numeric`, the named CHECK constraints, the `is_disabled`/`retry_count` defaults round-tripping, and JSON columns accepting/returning `None` as SQL `NULL`. (Belt-and-suspenders for the things §4.3 most cares about, independent of autogenerate.)
5. **One-command local bootstrap** — `docker compose up -d --wait db` + documented steps bring up a working dev environment; a seed script runs on PG.
6. **SQLite absent from app + test code, grep-clean — including comments.** After the conftest rewrite and the migration-test deletion, the only remaining SQLite references are stale *comments* describing old naive-datetime behavior (`api/helpers.py`, `auth.py:152`, `superuser/service.py:50`, `api/superuser.py:40`, `api/enrollment.py:18-20`, `test_run_render.py:87`); sweep them (and re-check `helpers.py`'s normalization comment/logic under `TIMESTAMPTZ`).

## Risks & rollout
- **Conftest redesign touches load-bearing fixtures.** Mitigation: preserve the exact shared-session behavior; change only schema-build + isolation + engine unification. Highest-attention part of the slice; gets the strict per-task review.
- **Autogenerated initial migration is imperfect.** Mitigation: the explicit review checklist (§4.3), the no-drift test (criterion 3), and the independent semantic assertions (criterion 4).
- **Latent Postgres-strictness bugs.** Mitigation: the step-0 early full-suite run enumerates the real set; each fix is a real bug caught, not a regression introduced.
- **Rollback:** the branch is revertable wholesale before merge; nothing is deployed.

## Suggested task ordering (for the plan phase)
There is a hard dependency chain — two steps cannot move earlier:
1. Driver swap + `config.py` default + `database.py` engine/pool → 2. `docker compose up -d --wait db` (live PG so models import + autogenerate can run) → 3. delete the 16 migrations + `alembic revision --autogenerate` + §4.3 review → 4. `env.py` `compare_server_default`/`compare_type` + `is_disabled` normalization → 5. minimal PG conftest (env-var wiring, session schema build, truncate) → 6. **run full suite early**, record baseline → 7. fix-pass (delete migration-test file, rewrite PRAGMA-FK-off tests, fix inverted tz assertion, add `ORDER BY`s) → 8. no-drift test + semantic-assertion test → 9. docs/runbook + dev-script updates.
