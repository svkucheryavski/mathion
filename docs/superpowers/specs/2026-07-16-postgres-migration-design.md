# Postgres Migration (Phase 9-A1) — Design

**Status:** Draft — revised after two 5-reviewer Opus rounds + two codex passes (awaiting user review)
**Date:** 2026-07-16
**Scope:** Backend + dev/test infrastructure only. Frontend untouched.

## Context

Mathion runs on SQLite today (`create_engine("sqlite:///./mathion.db")`; tests on in-memory SQLite). Phase 9-A (concurrency hardening) requires PostgreSQL — the race fixes are `SELECT ... FOR UPDATE` / advisory locks / SAVEPOINT-retry, which SQLite cannot express (it serializes all writes behind one global write lock). Postgres is also the intended production database for an LMS whose real workload is concurrent writes (a class of up to ~200 students, ≤10 per group, submitting near a deadline).

Decision (locked with the user): **move Mathion entirely to PostgreSQL — dev, test, and production — and drop SQLite support completely.** Rejected alternatives: "keep both" (divergence tax; SQLite tests mask Postgres behavior — the exact masking that motivated this) and "SQLite in production" (single-writer lock is wrong for the submission-rush workload, and it makes the concurrency slice moot).

Phase 9-A decomposes into two independently shippable slices:
- **A1 — Postgres migration (THIS spec):** app + tests + dev on Postgres, one clean initial migration, full suite green. No locking changes.
- **A2 — Concurrency hardening (next slice):** the ~13 race sites fixed and verified with real concurrency tests on Postgres.

## Goal

The application, the full test suite, and local development all run on PostgreSQL. SQLite is removed from the codebase. Production is configured via a single `MATHION_DATABASE_URL` env var (works for managed hosts *and* self-hosted Postgres). Deliverable is standalone: nothing about locking changes here.

## Non-goals

- **Concurrency / locking fixes** — that is A2. A1 must not change any read-then-write or capacity logic. (One narrow exception: the §7 Postgres-portability fixes — deterministic `ORDER BY` tie-breaking (including decision-driving selections such as the latest-PIN pick) and bounded-type input handling (a clean 4xx or documented truncation instead of a silent store) — change *undefined or latent* behavior, not locking or product logic. Postgres would reject the oversized values and non-deterministically order the ties anyway; A1 only controls the API error and makes selection deterministic.)
- **Choosing a production host.** Config is `MATHION_DATABASE_URL`-driven; hosting (Neon / Supabase / Railway / Render / Fly / self-hosted) is decided later.
- **Data migration.** Production is not live and dev data is disposable (seed scripts). Fresh database + `alembic upgrade head` + reseed. No migration of existing rows.
- **Frontend changes.** None.

## Locked decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Databases | Postgres for dev + test + prod; drop SQLite | Concurrency correctness + prod target; no divergence tax |
| Driver | **psycopg3** (`psycopg[binary]`), `postgresql+psycopg://` | Actively developed; one package family for dev (binary) and self-hosted prod; SQLAlchemy 2.0-recommended. Replaces the incidental `psycopg2-binary`. Self-hosted prod *may* later prefer `psycopg[c]`; noted, not required for A1. |
| Postgres version | **17** for dev/CI | Deliberate conservative pin: stable, proven, supported through 2029. Not the newest (PG18 is current as of mid-2026) — chosen for maturity; `MATHION_DATABASE_URL` lets any host override. |
| Prod config | `MATHION_DATABASE_URL` env var only | Portable across managed + self-hosted |
| Session timezone | **Pin `TimeZone=UTC`** on every connection | Matches the app's UTC conventions; makes returned offsets + JSON serialization deterministic regardless of host/session TZ (see §Error-handling) |
| Migrations | **Reset**: delete the 16 SQLite-era migrations, replace with ONE autogenerated Postgres-native initial migration | No data to preserve; drops `batch_alter_table` shims + one-time SQLite data-backfills; simpler to trust |
| Test schema | Built by running the real migration(s) (`alembic upgrade head`) once per session | Guarantees test schema == prod schema; residual drift is caught by criteria 3+4 (`compare_metadata` does not cover every schema feature, so the reflection checks are load-bearing, not redundant) |
| Test isolation | `TRUNCATE ... RESTART IDENTITY CASCADE` between tests | Real commit semantics like prod; **won't fight A2's app-level SAVEPOINTs / row locks** the way a savepoint-rollback harness would |
| Test DB wiring | **One engine**: the test process **assigns** `MATHION_DATABASE_URL` = the test DB (a *distinct* `mathion_test` database) *before* importing `mathion.config`; app + harness share `mathion.database.engine` | Avoids a dual-engine hazard where app code that opens its own `SessionLocal()` (dispatcher, CLI) targets a *different* DB than the harness built (see §5). Plain assignment (not `setdefault`) + a distinct DB name + a canonical-identity guard are load-bearing safety rails (see §5) |

## Architecture / components

### 1. Dependencies (`backend/pyproject.toml`)
- Add `psycopg[binary]` (psycopg3). Remove `psycopg2-binary` (currently at `pyproject.toml:13`; incidentally installed, imported nowhere in app/test/script code — verified).
- SQLAlchemy 2.0.49, Alembic 1.18.4, FastAPI 0.136, uvicorn 0.44 unchanged.

### 2. Configuration & engine
- `config.py` (`Settings`, `env_prefix="MATHION_"` → the field maps to `MATHION_DATABASE_URL`): the `database_url` field **defaults to the local docker Postgres URL** (`postgresql+psycopg://mathion:mathion@localhost:5432/mathion`) for zero-config dev, overridden by `MATHION_DATABASE_URL` in test/prod. **No SQLite default, no SQLite fallback.**
- **Prod localhost-default footgun:** a prod deploy that forgets `MATHION_DATABASE_URL` silently targets `localhost`. It fails loud (connection refused) rather than corrupting data, but to match the existing "insecure dev default" warnings (`secret_key`, `cookie_secure`): on startup (in the lifespan, so it fires on real uvicorn boot — *not* on every `mathion.database` import under alembic/CLI/tests), log one line echoing the **password-redacted** target host/db, and document `MATHION_DATABASE_URL` as required-in-prod in the runbook.
- `database.py`:
  - Engine gains production-grade pool settings: `pool_pre_ping=True`, `pool_recycle` (e.g. 300–1800 s), `pool_timeout` (bound the wait on a saturated pool so exhaustion fails fast instead of hanging), a modest `pool_size` + `max_overflow`, and `connect_args`. Concrete values chosen in the plan and sized against the worker model (§8) — reserving +1 for the dispatcher's own pooled `SessionLocal()`.
  - `connect_args={"connect_timeout": …, "options": "-c statement_timeout=… -c TimeZone=UTC"}`: a configurable server-side **`statement_timeout`** (basic operability — a runaway query shouldn't pin a scarce connection; `lock_timeout` proper is A2's locking concern) **and a pinned `TimeZone=UTC`** (session-timezone decision, §Locked decisions / §Error-handling). SSL for managed hosts is **URL-driven** (`?sslmode=require`) — do not add a redundant `connect_args` for it.
  - **Delete `enable_sqlite_fk`** (`database.py:22-33`) and its `PRAGMA foreign_keys=ON` listener — Postgres enforces foreign keys (incl. the models' `ondelete` CASCADE/RESTRICT/SET NULL) natively and unconditionally.
- No SQLite branch remains anywhere in app code. (Verified: `database.py:22-33` is the only SQLite branch in app code; `config.py:9` default is the only other SQLite reference.)

### 3. Local dev provisioning
- `docker-compose.yml` at repo root: a `postgres:17` service with a named volume, a healthcheck, and env for db/user/password. **`POSTGRES_DB`/`POSTGRES_USER`/`POSTGRES_PASSWORD` must equal the config default URL's `mathion`/`mathion`/`mathion`** so zero-config dev + the one-command bootstrap (criterion 5) work. (The image auto-creates `POSTGRES_DB=mathion`; the built-in `postgres` maintenance DB the test fixture uses always exists.)
- `.env.example` documenting `MATHION_DATABASE_URL` (and the test URL). **Note:** `Settings.model_config` sets only `env_prefix`, no `env_file`, so the app process does **not** auto-load `.env`. The plan will either add `env_file=".env"` to `model_config` **or** state in the runbook that `.env` is for compose/`export` only. (Post-migration the default is a *Postgres* URL, so a dev relying on `.env` for a non-default host must `export` it.)
- Bootstrap becomes: `docker compose up -d --wait db` → `alembic upgrade head` → `python -m scripts.seed_*`. The `--wait` gates on the healthcheck so a host-run `alembic upgrade` cannot race a not-yet-ready container. Documented in the README/runbook.
- **Update the existing dev scripts** (they *are* the runbook and currently assume SQLite): `run-debug.sh` (bare `uvicorn --reload`, no DB provisioning) and `run-dashboards-smoke.sh:24-28` (`rm -f mathion.db` + `alembic upgrade head`). Rewrite to the `docker compose up -d --wait db` flow. (`run-dashboards-smoke.sh` is currently untracked; the plan touches it explicitly.)

### 4. Migration reset (single Postgres-native initial migration)
The models (`Base.metadata`) are the source of truth for the reset: we **regenerate the migration FROM the models**, so migration == models by construction. (Nuance: several columns carry a model-level Python `default=` with **no** `server_default` — `mini_projects.is_published`, `submissions.is_late`/`is_resubmission`, `course_versions.label`, `blocks.info_html`, the two `is_disabled` at models_auth.py:16 / models.py:43. Safe because the app inserts exclusively via the ORM, which applies `default=` on INSERT. Old SQLite-era migrations carried extra `server_default`s the models omit; the reset intentionally drops those. Accurate framing: "new migration == models," **not** "models == old effective schema." Codex confirmed no *behavioral* element lives only in the old migrations: the old-only items are backfills, those extra defaults, explicitly-named FKs, and the named unique index on `evaluations.submission_id` — the last becoming a behaviorally-equivalent unique-constraint-backed index from the model.)

The **one** boolean column with a literal `server_default` is `Group.is_disabled` (models.py:236, `server_default="0"`); it is normalized to `sa.text("false")` (§4a) **before** autogeneration, so the generated file is Postgres-native from the start.

All 27 tables register on `Base.metadata` when `alembic/env.py` imports the two model modules (importing `mathion.models` also imports the auth models at models.py:376, so `SuperuserPanelToken` and `NotificationLogEntry` register despite env.py's partial name lists).

Procedure:
1. Stand up a fresh Postgres (driver + docker PG must land first); delete the 16 files under `alembic/versions/`.
2. Normalize `is_disabled` to `sa.text("false")` (§4a), then `alembic revision --autogenerate -m "initial schema"` from the models against the empty Postgres.
3. **Review the generated migration carefully.** A `create_table` block renders `server_default`, `CheckConstraint`, `UniqueConstraint`, `Index`, and FK `ondelete` regardless of any `compare_*` flag; this checklist confirms it:
   - `DateTime(timezone=True)` → `TIMESTAMP WITH TIME ZONE`.
   - `Numeric(20,10)` (models.py:136) preserved.
   - `server_default=func.now()` on the 31 timestamp columns present.
   - `server_default`: `retry_count` (Integer, models_auth.py:112) and normalized `is_disabled` (`sa.text("false")`, models.py:236) present.
   - Named `CheckConstraint`s (`ck_evaluation_result_enum`, `ck_mini_project_*`, `ck_submission_*`, `ck_evaluation_*`) present — statuses are `String(20)` + CHECK, not native enums (no `Enum()` anywhere).
   - **JSON columns** (`last_answers` models_auth.py:96 nullable, `payload` :109 non-null) render as PG `json` (not `JSONB`).
   - All indexes, `UniqueConstraint`s (incl. the unnamed unique constraint from `evaluations.submission_id` `unique=True`, models.py:338, which PG backs with a unique index), and FK `ondelete` rules match the models. (Old `fk_*` names become PG-default `<table>_<col>_fkey`; zero behavioral impact, no code references FK names — A2 `naming_convention` follow-up in Open items.)
4. That migration is base + head. `alembic upgrade head` provisions prod and the test schema.
5. One-time data-backfill logic from the old chain is intentionally dropped — it fixed data that won't exist on a fresh database.

Old migration files remain in git history for archaeology.

### 4a. Alembic drift configuration & URL handling (`alembic/env.py`)
`env.py:28` unconditionally routes `settings.database_url` through `config.set_main_option("sqlalchemy.url", …)` (Alembic's `ConfigParser`), and its online `context.configure()` (line 50) sets neither `compare_type` nor `compare_server_default`. Changes:
- **URL / percent footgun — mandate ONE complete variant (codex Important).** `ConfigParser.set()` itself rejects a lone `%` (a normal encoded credential like `p%40ss`), so it isn't enough to make online mode ignore the configured value — *and* merely deleting line 28 breaks **offline** mode, which still reads the INI placeholder at `env.py:37` (`url = config.get_main_option("sqlalchemy.url")`). **Required design:** remove the global `set_main_option("sqlalchemy.url", …)` entirely; in `run_migrations_online` build the engine directly from `settings.database_url`; in `run_migrations_offline` call `context.configure(url=settings.database_url, …)` directly. Alembic temporarily owning its own migration engine is compatible with the "one engine" test design — that invariant is that app requests, fixtures, and direct `SessionLocal()` share one *application* engine/URL, which the env-var-before-import wiring (§5) guarantees; the criterion-3 test builds its own `MigrationContext` and is unaffected. Test **both** a real online migration/autogenerate **and** `alembic upgrade --sql` (offline) with a `%`-encoded credential.
- **Comparison flags:** set `compare_type=True` and `compare_server_default=True` explicitly in the **online** `context.configure()`. This governs CLI `alembic revision --autogenerate` and any future drift-check path. (Pin both; the criterion-3 test (§4b) sets the same flags on its own `MigrationContext`.)

### 4b. No-drift verification (success criterion 3)
The no-drift test builds a `MigrationContext` with `compare_type=True` + `compare_server_default=True` and asserts `compare_metadata(context, Base.metadata)` returns an **empty** diff (in-process via `alembic.autogenerate.compare_metadata` — not by shelling out). `compare_metadata` does **not** compare CHECK constraints or FK `ondelete`, so those are covered exhaustively by criterion 4 (complementary, not redundant). Determinism:
- The known phantom-diff source (`is_disabled` boolean `"0"` vs PG `false`) is removed by the `sa.text("false")` normalization (§4a).
- The reset *helps* the `func.now()` columns: old migrations used `sa.text('(CURRENT_TIMESTAMP)')` (SQLite-ism) which would phantom-diff; regenerating renders `now()`, which reflects cleanly.
- **Verify-during-tuning** (not assumed clean): `is_disabled` (post-normalization), `retry_count` (`'0'::integer` cast-stripping), the `evaluations.submission_id` unique-constraint index. §4b budgets tuning of residual false-positives (function-default text, implicit indexes) until the diff is genuinely empty.

### 5. Test harness redesign (`backend/tests/conftest.py`)
Current: a **separate** in-memory SQLite engine (`test_engine`, `StaticPool`, `check_same_thread`), `create_all`/`drop_all` per test (autouse `setup_db`), `db` = session on `test_engine`, `client` overrides `get_db` to yield the **same** `db` session (app+test share one session — load-bearing for `_assert_hidden`, unpublish-then-GET). `test_engine` is *not* the app's `mathion.database.engine`.

**Dual-engine hazard (must fix, not inherit):** `mathion.database.engine`/`SessionLocal` bind to `settings.database_url` at import; `get_db`'s override only redirects the *request* path. `SessionLocal()` is opened directly by the dispatcher loop (`dispatcher.py:215`) and superuser CLI (`superuser/__main__.py:20`). `test_notifications_lifespan.py::test_lifespan_shutdown_with_inflight_tick` starts the **real** lifespan and drives `run_forever → _do_tick → SessionLocal()` against `settings.database_url` (the `test_notifications_lock.py` cases do not reach the tick path). On SQLite this hit a stray `./mathion.db`; on PG it would hit the dev DB or raise `OperationalError` (swallowed → green for the wrong reason).

Target (preserves shared-session semantics; unifies onto one engine):
- **Env-var-before-import, by ASSIGNMENT:** at the top of `conftest.py` (alongside the existing `os.environ.setdefault("MATHION_EMAIL_MODE", …)` at conftest.py:10-12), first **capture** the pre-existing `os.environ.get("MATHION_DATABASE_URL")` (for the guard below), then **assign** (not `setdefault`) `os.environ["MATHION_DATABASE_URL"]` = the test DB URL *before* importing `mathion.config`/`mathion.database`. The URL comes from a dedicated `MATHION_TEST_DATABASE_URL` (CI-overridable), defaulting to a **distinct** `mathion_test` database. Assignment is a **data-loss guardrail**: the harness runs `DROP SCHEMA public CASCADE` + per-test `TRUNCATE`, so it must never inherit an exported dev/prod URL — it forces the test DB unconditionally. (Deliberately unlike the email-mode `setdefault`, whose worst case is harmless.)
- **`pytest_configure` guard (runs at collection, before any fixture) — the last rail before `DROP SCHEMA`; compare CANONICAL IDENTITY, not raw strings (codex-sharpened):** string (in)equality does not establish database (in)equality — `localhost` vs `127.0.0.1`/`::1`, omitted vs explicit `:5432`, driver spelling, percent-encoding, and query-arg ordering can all mask the same target. Require **all** of: (a) the parsed database name (`make_url(settings.database_url).database`, not a substring match) matches a strict pattern `mathion_test` / `mathion_test_*`; (b) the test target's **canonical connection identity** — (resolved host, effective port defaulting 5432, database, user) — is **not equal** to the captured pre-overwrite application URL's canonical identity, failing **conservatively** (abort) when equivalence is uncertain; (c) a non-local host requires an **exact affirmative** opt-in value (not generic truthiness). A failing guard aborts the run. Document the residual: an SSH tunnel presenting a remote DB as `localhost` cannot be detected — an operational assumption, not a code guard. (Mirrors/extends the email-mode `pytest_configure` assertion at conftest.py:22.)
- **One engine:** delete conftest's separate `test_engine`/`TestSession`; the `db` fixture opens a session on `mathion.database.engine` (`SessionLocal`). `client` still overrides `get_db` to yield that same session.
- **Session-scoped schema build (`autouse`, session-scoped):** ensure the test database exists — AUTOCOMMIT connect to the maintenance DB (`postgres`; the role needs `CREATEDB`, satisfied by the docker/CI `postgres` superuser), check `pg_database`/catch `DuplicateDatabase`, `CREATE DATABASE mathion_test` if absent — then `DROP SCHEMA public CASCADE; CREATE SCHEMA public` (requires the test role to **own** the test DB, true when the maintenance connection created it as `mathion` — note for self-hosted CI with a non-owner role) and `alembic upgrade head`. DROP-SCHEMA makes the session robust to a stale schema from a prior run on old revisions.
- **Function-scoped isolation — teardown order ENCODED, not asserted (codex):** make `db` explicitly depend on an autouse function-scoped isolation fixture, so pytest's LIFO finalization closes/rolls back `db` *first* and the isolation fixture truncates *after*. It runs `TRUNCATE <all model tables> RESTART IDENTITY CASCADE` in a single statement (leaving `alembic_version` intact; table list from `Base.metadata.sorted_tables`), under a short `lock_timeout` so a leaked background transaction fails *diagnostically* instead of hanging. (Verified: no test asserts a specific autoincrement id or relies on cross-test id state — only the intentional-nonexistent `99999`/`999999` — so `RESTART IDENTITY` is safe.)
- **`client` fixture:** keep yielding a bare `CSRFTestClient(app)` **without** a context manager — the current behavior (conftest.py:95) deliberately does not run the app lifespan, which keeps the dispatcher from starting in ordinary tests; only explicit lifespan tests enter `with TestClient(app)`. (Blanket-context-managing would start the dispatcher loop for every test. The client opens no session of its own, so there's no connection-cleanup gap; a bare `.close()` after yield would be harmless hygiene but is not required.)
- Remove SQLite-only bits (`StaticPool`, `check_same_thread`, the pragma listener at conftest.py:69-73).
- The `db.rollback()` in `test_patch_evaluation_as_admin_succeeds` is a no-op for already-committed data — same as production.
- **Concurrency watch (step-0 run):** under one engine, `test_lifespan_shutdown_with_inflight_tick` now runs the dispatcher on a real second connection concurrently (previously serialized on in-memory SQLite) and becomes a *meaningful* mid-shutdown test still asserting only "no leaked task." The `__aexit__` drain completes before teardown; the cleanup `lock_timeout` converts any drain-timeout edge case into a diagnostic failure, not a hang.

**CI provisioning:** a `postgres:17` service container; the assign-env-var + session-fixture path runs unchanged. pytest-xdist parallel workers (one DB/worker) — out of scope now.

### 6. Seed scripts
- `scripts/seed_*.py` are all ORM-only (no raw SQL/`text()`/`PRAGMA`/`.db` paths/autoincrement reliance) and open `SessionLocal` from `mathion.database` — verified portable; bind to PG post-migration and run unchanged.

### 7. Query portability fixes (SQLite → Postgres)

**7a. Deterministic ordering — a RULE, not a hand-list (codex).** SQLite tie-broke by rowid even under a non-unique `ORDER BY`; Postgres guarantees neither ordering nor tie-break. The enumeration was proven incomplete more than once. Replace it with a checked rule and sweep every query:

> **Rule:** every `ORDER BY` whose result is externally observable (returned to the UI/API) or drives a mutation/selection decision must end in a **unique** tie-breaker (normally `.id`).

Known sites (illustrative — the **rule** is authoritative; sweep for the rest):
- **Fully unordered (real bug):** `courses.py:45`, `:65` → `.order_by(Course.id)`; `enrollment.py:118` (roster to UI) → stable key.
- **Non-unique `order` column** (no unique constraint on `order`): `blocks.py:109`, `:286`, `items.py:99`, the content/question/answer-option order queries, version-clone traversal, and the ORM relationship `order_by="…"` collections (e.g. models.py:55) that feed serialization → append `.id`.
- **Non-unique timestamp/date** (most tie-prone — `func.now()` = transaction-start-time, so rows in one transaction share a value): `run_roster.py:120`, `dashboard.py:161`, `run_teachers.py:62` (`created_at`), `submissions.py:252`/`:264` (`submitted_at`), `runs.py:69`/`student_mini_projects.py:95` (`start_date`) → append `.id`.
- **Decision-driving selections** (a tie changes *which row wins*): `auth.py:105` (`LoginPIN.created_at.desc()` + `.first()` — latest-PIN pick), `helpers.py:81` (published-version selection), `student.py:158`/`:232` (enrollment dedup/selection), `dashboard.py:56`/`:540` → append `.id`.
- **Already unique within the query's parent scope — a secondary `.id` is redundant (harmless), do NOT count as gaps:** `groups.py:44` (`Group.name`, uq_group_run_name), `assets.py:117` (`Asset.filename`, uq_asset_version_filename), `run_assets.py:222` (`RunAsset.filename`, uq_run_asset_run_filename).
- Mirror the already-correct pattern: `dispatcher.py:103-104`, `versions.py:199-201`.

**7b. Postgres bounded-type enforcement — latent bugs the suite won't surface (codex).** SQLite ignores `VARCHAR(n)`, `NUMERIC(p,s)`, **and `INTEGER` (int4) range**; Postgres raises **`DataError`** on overflow. A RULE, again, because the create-schema-only enumeration was incomplete:

> **Rule:** every inbound field whose value reaches a bounded SQL column — `VARCHAR(n)`, `NUMERIC(p,s)`, or `INTEGER` (int4, max 2,147,483,647) — must carry a matching validation (returning a clean 4xx), **on every write schema** (create *and* update/edit *and* batch), or its write path must catch `DataError` and translate it. "Full suite green" will not catch these — no test exercises the boundary (criterion 7).

Known mismatches (sweep for more):
- **VARCHAR:** `video_url` (schemas.py:129 create **and** :172 update) → `String(500)`; `correct_text` (:309 create **and** :317 update) → `String(500)`; asset `filename` (`sanitize_filename` assets.py:29, no cap) → `String(255)` — **truncate** the sanitized base to keep the full result ≤255 preserving the extension (derived name; truncation beats rejecting a valid upload; a post-truncation collision stays a 409); `EnrollBatchRequest.emails` (schemas.py:244, `list[str]` no per-element bound) → `User.email String(254)` via `enrollment.py:98` → `get_or_create_user` (helpers.py:65 catches only `IntegrityError`); batch-roster `name` (schemas.py:501) → `User.full_name String(200)` and `group` (:503) → `Group.name String(80)` at `run_roster.py:216`/`:224`.
- **NUMERIC:** `correct_numeric` (:307 create **and** :315 update) → `Numeric(20,10)`: `Field(max_digits=20, decimal_places=10)`.
- **INTEGER (int4):** `Question.precision` (:308 create **and** :316 update, only `ge=0`) → `Integer` (models.py:137): give a semantic upper bound (≤ the numeric scale, e.g. 10); `ReorderItem.order` (:363, only `ge=1`) and the block/sequence/item/question/option `order` create-fields → `Integer`: bound ≤ 2,147,483,647. Both are flushed/committed without a DB-exception wrapper (`questions.py:67`, `:157`), so an int4 overflow is an uncaught 500.

Approach: validate upstream (preferred) so the client gets real 422 feedback. Endpoints that catch only `IntegrityError` (`assets.py:74`, `helpers.py:65`) do not catch `DataError`; the generic per-row batch handler (`run_roster`) prevents a whole-request 500 but returns a *misleading* internal error for oversized input — validate upstream so the row gets real feedback. Criterion 7 covers **every inbound bounded SQL type (VARCHAR/NUMERIC/INTEGER)**, not only strings.

### 8. Worker / connection-pool sizing
Default `QueuePool` allows up to `pool_size (5) + max_overflow (10)` = 15 connections **per process**; managed hosts cap low. The plan states the assumed worker model and sizes to `pool_size × workers + max_overflow × workers ≤ host max_connections`, **reserving +1 for the dispatcher's pooled `SessionLocal()`** (`dispatcher.py:215`, same per-process pool). The dispatcher's singleton flock (`dispatcher.py:21-45` → `RuntimeError` on the second holder, acquired at `main.py:53-54` only when email is enabled) effectively forces **one** uvicorn worker whenever email is on — the realistic A1 target is single-worker; the formula still governs the email-disabled multi-worker case. Deferred to deploy-time: transaction-mode poolers break psycopg3's server-side prepared statements → `prepare_threshold=None`/session mode; and a `%`-in-URL runbook note (§4a resolves the alembic path; the app engine reads the URL directly so is unaffected).

## Data flow: bootstrap
- **Dev:** `docker compose up -d --wait db` → `alembic upgrade head` → seed → `uvicorn`.
- **Test:** session fixture (ensure DB exists → DROP/CREATE schema → `alembic upgrade head`) → run tests (TRUNCATE between) → done.
- **Prod:** set `MATHION_DATABASE_URL` → `alembic upgrade head` (explicit deploy step, not app-boot autorun) → run. No data import.

## Error handling / edge cases (Postgres strictness)
Postgres is stricter than SQLite's flexible typing. Much of the fallout is knowable now (§7b VARCHAR/NUMERIC/INTEGER, plus below); the plan budgets a fix pass for anything the step-0 run surfaces:
- **Tests that baked in SQLite's tz-stripping and now invert:** `test_notifications_dispatcher.py:230-232` asserts `next_attempt_at == (now + …).replace(tzinfo=None)`; under `TIMESTAMPTZ` the read-back is tz-aware. Fix: drop `.replace(tzinfo=None)`, compare aware-to-aware. (Only `.replace(tzinfo=None)` in the tree.)
- **In-test `PRAGMA foreign_keys=OFF` — per-FK rewrites:**
  - `test_notifications_dispatcher.py:74-85` inserts `user_id=999999` via PRAGMA-off. `NotificationLogEntry.user_id` is `ondelete="CASCADE"` + `nullable=False` (models_auth.py:107): PG-impossible row, branch unreachable in prod. **Delete this test** (its `LookupError` contract stays covered by `test_build_render_context_missing_run_raises`).
  - `test_run_assets.py:234-267` inserts `uploaded_by=99999` via PRAGMA-off. `RunAsset.uploaded_by` is `ondelete="SET NULL"` (models.py:363). **Rewrite:** create the asset with a **fresh bare throwaway user** (no submissions/evaluations — else the RESTRICT FKs at models.py:309/339 block the delete), then hard-DELETE that user; the SET NULL cascade nulls `uploaded_by`, same assertion. Update the moot docstring.
- **`func.now()` = transaction-start-time** — the mechanism behind §7a's timestamp tie-breaks; two default timestamps in one transaction are *equal*.
- **Timestamp semantics — DECIDED: pin `TimeZone=UTC` on every connection** (via `connect_args` `options`, §2). Reflection proving a column is `TIMESTAMPTZ` proves storage, not returned-offset determinism; pinning UTC matches the app's UTC conventions and makes returned offsets + JSON serialization deterministic regardless of the host/session TZ (the stored instant is correct either way). Criterion 4 asserts `SHOW TimeZone == 'UTC'` and a semantic instant round-trip.
- **tz-naive datetime WRITES — confirmed absent:** every `datetime.now(...)` passes `timezone.utc`; `to_utc_aware()` (`helpers.py`) and `.tzinfo is None` guards defend the read-back.
- **JSON `None` (clarified, NOT a portability difference):** with bare `JSON` (default `none_as_null=False`), an *explicitly-set* `None` persists as JSON `'null'` (not SQL NULL) — **identically on SQLite and PG** (type-level bind). The app never assigns `None` (`last_answers` only set to a dict at `quiz.py:132` or left unset; `payload` is `nullable=False`), so an *unset* nullable JSON column lands as SQL NULL. **Do not add `none_as_null=True` in A1.** Criterion 4 asserts round-trip + unset→`IS NULL` (verified with a `col IS NULL` query, since JSON `'null'` also deserializes to Python `None` so an ORM `== None` check is insufficient), never explicit-`None`→SQL-NULL.
- **Confirmed absent** (so the plan doesn't chase non-issues): case-sensitive `LIKE` (no `.like()`/`.ilike()`; `=` email lookups exact on normalized lowercase), raw SQL outside `database.py`, `rowid`/`AUTOINCREMENT` reliance, `IntegrityError` message-string inspection (all handlers generic 409s), boolean/integer string coercion (all boolean predicates are typed-column comparisons), `GROUP BY` strictness (all grouped queries list non-aggregate columns or group by a functionally-dependent PK), NULL-ordering (no `ORDER BY` on a nullable column that can appear in its result set), `DISTINCT ON`/`LIMIT`, SQLite collation. SPA static mount / asset filesystem is DB-independent; `.gitignore` covers `*.db`.

0. **Run the full suite EARLY** — minimal PG conftest (assign-env-var + guard + session schema build + truncate) first, run the whole suite before polishing fixtures, record the failure set. Known: the deleted migration-round-trip file, the two PRAGMA-FK-off tests, the inverted tz assertion. §7b boundary bugs will **not** appear here — they need dedicated tests (criterion 7).
1. **Full suite green on Postgres.** **Baseline count changes**: `test_notifications_migration.py` is **deleted** (hardcodes `sqlite:///`, `PRAGMA table_info`, up/down round-trips against the deleted revisions `2f3e694d3544`/`378c62a02d4e`, and a `batch_alter_table` source assertion — none survive the reset; the one non-obsolete bit is re-covered by criterion 4), and `test_build_render_context_missing_user_raises` is deleted (PG-impossible). 2. **Migrations apply clean** on a fresh Postgres.
3. **No schema drift** — in-process `compare_metadata` (with `compare_type=True` + `compare_server_default=True`) returns an **empty** diff (§4b). ("Drift impossible" is too strong — this test plus criterion 4 are what *catch* drift.)
4. **Semantic schema assertions (exhaustive where the gate is otherwise blind).** A reflection test confirms: `TIMESTAMPTZ` on the tz columns; `Numeric(20,10)` on `correct_numeric`; **every named model CHECK constraint** present (`inspect().get_check_constraints()` — not a spot-check list; `compare_metadata` is blind to CHECKs); **every model FK's normalized `ondelete`** matches the reflected FK, matched by (table, constrained columns, referred table/columns) via `inspect().get_foreign_keys()` (not spot-checks — a hand-edited migration can otherwise drop any unspotted CASCADE/RESTRICT/SET NULL while criteria 3+4 both pass); the `is_disabled`/`retry_count` defaults round-tripping. **JSON:** round-trip (`None` in → `None` out for `last_answers`) and unset→`IS NULL` via a `col IS NULL` query — not explicit-`None`→SQL-NULL. **Timestamp:** write a datetime with a **non-UTC offset**, aware; read it back **through a refreshed object / new session** (not the identity-map cache); assert tz-aware and equal UTC instant; assert `SHOW TimeZone == 'UTC'`.
5. **One-command local bootstrap** — `docker compose up -d --wait db` + documented steps bring up a working dev env; a seed script runs on PG.
6. **SQLite absent from app + test code, grep-clean — including comments.** Remaining stale *comments* after the rewrite/deletion: `api/helpers.py:40`, `auth.py:152`, `superuser/service.py:50`, `api/superuser.py:40`, `api/enrollment.py:18-20`, `test_run_render.py:87`, plus the two rewritten test files (`test_notifications_dispatcher.py:76,230`, `test_run_assets.py:240`). Sweep them (re-check `helpers.py`'s normalization comment/logic under `TIMESTAMPTZ`). Also the §7a ordering-rule sweep.
7. **Bounded-type boundary tests (codex) — every inbound bounded SQL type (VARCHAR/NUMERIC/INTEGER), not only strings.** For each §7b field (and any the sweep finds), a test sends over-bound input and asserts a clean 4xx (or documented truncation) — **never** an uncaught 500/`DataError`. This is the coverage "full suite green" cannot provide.
8. **Cleanup fixture is proven, not vacuous.** A harness test seeds **committed sentinel rows** in several tables, invokes the exact cleanup helper the isolation fixture uses (after closing its session), then asserts — from a **new** connection — that every model table is empty (so it can't pass merely because nothing was inserted), with `alembic_version` intact.
